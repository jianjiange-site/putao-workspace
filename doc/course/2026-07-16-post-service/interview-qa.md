## 高频问题

### Q: 如何设计一个高并发的计数系统？

**考察点**：缓存应用、数据库优化、系统设计

**标准答案**（STAR法则）：

**Situation（场景）**：
> 在实习项目里，我负责帖子服务的点赞功能。约会 App 的爆款帖子可能 1 秒内 1000 人同时点赞，这是一个典型的高并发计数场景。

**Task（任务）**：
> 遇到的问题是：如果每次点赞都直接 UPDATE 数据库，PostgreSQL 的单行锁会串行化所有请求，导致第 1000 个用户要等 3 秒才能得到响应，而且会把数据库连接池占满，影响整个服务。

**Action（行动）**：
> 我采用了 Redis 写合并 + 批量刷盘的方案：
>
> 写路径：用户点赞时，只在 Redis 里做 INCR 操作，同时把 post_id 加入待刷盘 Set。整个过程 ~1ms 完成，不碰数据库。
>
> 读路径：返回点赞数时，用 DB 基准值 + Redis 增量，用户看到的是实时数据。
>
> 刷盘路径：每分钟定时任务从 Set 里取 100 个 post_id，用 Lua 脚本原子地把增量取出来，批量 UPDATE 到数据库。

**Result（结果）**：
> 1000 次点赞从原来需要 3000ms（串行）变成只需要 ~50ms（Redis 单命令），数据库压力从每分钟 1000 次 UPDATE 变成 1 次 UPDATE。

---

**追问准备**：

| 追问 | 答案 |
|------|------|
| 为什么 Lua 脚本要原子执行？ | 如果拆成 GET + SET 两条命令，在两次调用之间可能又有新点赞，导致数据被覆盖丢失。Redis 单线程执行 Lua 可以保证原子性。 |
| Redis 挂了怎么办？ | 数据库的基准值是真值，只是丢一分钟的增量。业务上可接受，而且有监控可以发现。 |
| 刷盘任务卡死了怎么办？ | updated_set 有 7 天 TTL 自动过期，监控会告警。 |
| 为什么不直接用 Redis 做持久化？ | Redis 是内存数据库，不适合做主存储。而且 Redis 也有宕机风险。 |

### Q: Redis 缓存和数据库一致性怎么保证？

**考察点**：缓存一致性、分布式系统

**标准答案**：

**常见模式对比**：

| 模式 | 做法 | 问题 |
|------|------|------|
| Cache Aside | 先写库，再删缓存 | 可能缓存穿透 |
| Read Through | 读时自动填充 | 实现复杂 |
| Write Through | 写时同步更新 | 延迟大 |
| Write Behind | 异步批量写 | 可能丢数据 |

**项目中用的是 Cache Aside**：

```
读：cache miss → 读 DB → 写缓存
写：写 DB → 删缓存（不是更新缓存）
```

**为什么删而不是更新？**

> 因为缓存的值可能很大，更新操作反而容易出错。删除缓存让下次读时自动重建更简单。

**先删缓存再写库行不行？**

> 不行。会导致脏读：A 删缓存 → B 读 → B 写缓存（旧值） → A 写库。正确的顺序是先写库再删缓存。

---

**追问准备**：

| 追问 | 答案 |
|------|------|
| 删缓存失败了怎么办？ | 可以重试，或者后续懒加载。不影响数据正确性。 |
| 缓存穿透怎么办？ | 可以设短 TTL，或者布隆过滤器过滤非法 key。 |
| 缓存雪崩怎么办？ | 缓存过期时间加随机值，或者用热点数据永不过期。 |

### Q: 如何设计一个 Feed 流系统？

**考察点**：系统设计、推荐算法、数据工程

**标准答案**：

**核心问题**：

> Feed 流需要解决三个矛盾：
> 1. 新鲜度和质量：太新可能质量差，太老可能没价值
> 2. 社交属性：好友发的要看到
> 3. 马太效应：热门内容越热，新内容没机会

**我的方案**：

> 我设计了三路池混合推荐：
>
> 1. **热门池**：按热度分排序，5 分钟重建一次。热度用 Hacker News 公式：（基础分 + 点赞×权重 + 评论×权重）/ 时间衰减
>
> 2. **好友时间线**：发推时写扩散到粉丝 timeline，读的时候直接拉
>
> 3. **冷启动池**：新帖子按时间顺序直接进这个池，给曝光机会

**位置分配**（10条为一页）：
> - 8 条来自热门池
> - 1 条来自好友时间线（第 3 位强插）
> - 1 条来自冷启动池（第 6 位扶持）

---

**追问准备**：

| 追问 | 答案 |
|------|------|
| 为什么选写扩散而不是读扩散？ | 约会 App 用户关注数有限（<500），读 Feed 要快。写扩散读 O(1)，适合这种场景。微博选读扩散是因为粉丝数无上限。 |
| 布隆过滤器干什么用？ | 已读去重。容量 5000，误判率 1%，7 天过期。 |
| 热门池 5 分钟重建一次会不会太慢？ | 热门内容排序有时间衰减项，每条内容分数随时间被动下降，不需要实时维护。5 分钟用户感知不到。 |
| 如何避免好友刷屏？ | 同好友单页最多出现一次。 |

### Q: 消息队列怎么保证消息不丢？

**考察点**：消息队列、可靠性设计

**标准答案**：

**三个环节都要保证**：

| 环节 | 保证方式 |
|------|----------|
| 生产者 | 同步发送 + retry + 确认机制 |
| Broker | 持久化到磁盘 |
| 消费者 | 手动 ACK + 幂等设计 |

**项目中的实践**：

> 生产者端：同步发送，本地 retry 3 次，超时 2s/次
> Broker 端：RocketMQ 默认持久化
> 消费者端：处理完成后 ACK，失败自动重投 16 次，仍失败转 DLQ

**消费幂等怎么保证？**

> ZADD 同 key 同 member 是覆盖语义，score 用发帖时间固定，重投不会有副作用。不需要额外幂等表。

---

**追问准备**：

| 追问 | 答案 |
|------|------|
| 发帖和发 MQ 消息怎么保证一致性？ | 接受小窗口：事务提交后发 MQ，MQ 失败不回滚。5 分钟后热门池重建可以兜底。如果业务要求强一致，需要加 Outbox 表。 |
| 消息顺序怎么保证？ | 同一帖只有一条消息，没有顺序问题。如果需要严格顺序，可以用 MessageQueue 的顺序消息。 |
| 消息重复怎么办？ | 消费者要保证幂等，上面说了。 |

### Q: 如何保证接口幂等性？

**考察点**：接口设计、数据一致性

**标准答案**：

**幂等的本质**：多次调用和一次调用的结果相同

**数据库层面**：

> 我在项目中用联合主键 + ON CONFLICT 实现：
> ```sql
> INSERT INTO post_likes (user_id, post_id, status, ...)
> VALUES (?, ?, ?, ...)
> ON CONFLICT (user_id, post_id)
> DO UPDATE SET status = EXCLUDED.status, ...
> WHERE post_likes.status <> EXCLUDED.status
> ```
> - 联合主键保证不会有两条相同记录
> - WHERE 条件过滤无效更新

**接口层面**：

> - 每个操作带上唯一请求 ID
> - Redis 存已处理的请求 ID，TTL 内不重复处理
> - 或者用数据库唯一索引

---

**追问准备**：

| 追问 | 答案 |
|------|------|
| 前端重复点击怎么办？ | 后端接口幂等，前端也可以加按钮防抖。 |
| 网络超时重试怎么办？ | 同样的请求带上唯一 ID，后端去重处理。 |
| 消息队列重复消费怎么办？ | 消费者保证幂等，上面说了。 |

## 场景问题

### Q: 如果让你设计一个评论系统，你怎么设计？

**考察点**：综合设计能力

**回答框架**：

1. **需求澄清**
   - 评论的层级（是否支持楼中楼）
   - 评论的排序（时间序/热度序）
   - 评论的分页

2. **数据模型**
   - 评论表：id, comment_id, post_id, user_id, content, root_id, parent_id, created_at
   - 索引：(post_id, root_id, created_at)

3. **核心接口**
   - 发评论
   - 删评论
   - 列表评论（游标分页）

4. **技术选型**
   - Redis ZSet 缓存最新 200 条
   - DB 做持久化和全量查询

5. **权衡取舍**
   - 为什么不用 MQ 异步写 ZSet？因为评论量级没那么大

### Q: 评论系统的楼中楼是怎么实现的？

**考察点**：嵌套评论结构设计、Redis ZSet 应用

**标准答案**：

>**表设计**：三个字段搞定嵌套

```
root_id = 0, parent_id = 0  → 一级评论（直接评论帖子）
root_id = A, parent_id = A  → 回复一级评论 A
root_id = A, parent_id = B  → 回复楼中楼 B（追溯到 A 为根）
```

> **读性能**：Redis ZSet 滑动窗口

> 帖子有一个 ZSet，members = commentId，scores = commentId（Snowflake 时间戳）。`ZREVRANGE` 天然按时间倒序，最多存 200 条，超出裁掉最老的。查到 commentId 后批量回库查详情。

> **写路径**：先写 DB → 再写 ZSet

> 评论先落库保证持久化，再写入 ZSet 做滑动窗口缓存。如果 ZSet 未命中（冷帖或超过200条），直接回源 DB。

**追问准备**：

| 追问 | 答案 |
|------|------|
| 为什么用 root_id 查楼中楼而不是 parent_id？ | parent_id 只查到直接子评论，root_id 才能查到该线程下所有回复 |
| ZSet 最大 200 条够吗？ | 超过 200 条回源 DB，实际体验影响不大；而且 200 条的 TTL 是 7 天，冷帖自动过期 |
| 评论数和点赞数能共用一套刷盘机制吗？ | 可以，都用 `SADD updated_set` 标记帖子，每分钟 Job 统一处理 |

### Q: 项目遇到过什么技术挑战？你怎么解决的？

**考察点**：问题解决能力、学习能力

**回答模板**：

> 我印象最深的是 Feed 热门池重建的性能问题。
>
> 一开始我按最直觉的写法：每条帖子都去 Redis 拿增量计数。结果一跑，5 万条帖子 × 2 次 Redis 调用 = 10 万次调用，耗时 30 秒，还超时了。
>
> 后来我改成 Pipeline 批量获取，5 万条帖子一次 Pipeline 拿完，耗时降到 2 秒。
>
> 经验教训：调用 Redis 要批量，不要逐条调用。

## 项目讲解话术

### 一分钟版本

> 我在实习期间负责帖子服务，这是一个约会 App 的核心模块，主要功能是发帖、点赞评论和 Feed 流推荐。
>
> 其中我最有收获的是点赞计数系统的设计。面对高并发点赞，我用 Redis 写合并 + 批量刷盘，把数据库压力从每分钟 1000 次 UPDATE 降到了 1 次。
>
> 另一个是 Feed 流推荐，我设计了三路池混合推荐——热门池保证优质内容曝光，好友时间线保证社交属性，冷启动池让新帖也有机会。

### 五分钟版本

> **背景**：帖子服务是整个 App 的内容核心
>
> **技术挑战 1 - 高并发计数**：
> - 问题：爆款帖 1 秒 1000 赞，直接 UPDATE 会单行锁串行
> - 方案：Redis INCR + 每分钟批量刷盘
> - 结果：性能提升 60 倍
>
> **技术挑战 2 - Feed 流推荐**：
> - 问题：新帖 0 赞排不上去，热门帖永远在前
> - 方案：三路池混合 + Hacker News 热度公式
> - 结果：兼顾新鲜度和质量
>
> **技术挑战 3 - 写扩散**：
> - 问题：用户发帖后要推送给所有粉丝
> - 方案：RocketMQ 异步消费
> - 结果：发帖接口 0 阻塞

> **技术挑战 4 - 楼中楼评论**：
> - 问题：评论列表访问量大，但评论本身改动少
> - 方案：Redis ZSet 滑动窗口缓存最新 200 条，commentId 作分数天然倒序
> - 结果：热帖评论列表全部走缓存，DB 零压力

## 面试注意事项

1. **不要背答案**，用自己的话讲，面试官看得出来
2. **代码是证据**，说到方案就要能讲清具体实现
3. **诚实**，不会就说不会，但可以讲思路
4. **主动引导**，把话题引到你熟悉的领域
5. **展示思考**，不仅讲 what，要讲 why 和 trade-off
