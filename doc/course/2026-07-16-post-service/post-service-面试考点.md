# Post Service 面试考点

> 本文基于 `post-service-业务清单.md`、`post-service-业务流程详解.md`、`post-service-特殊场景设计.md` 以及当前实现整理。
> 面试回答时不要只说“使用了 Redis、Caffeine、RocketMQ”，还要说明数据特征、一致性要求、失败场景、方案取舍和生产边界。

## 一、服务整体设计

### 1. Post Service 负责哪些业务？

主要职责包括：

- 发布、查询、删除帖子；
- 帖子图片管理；
- 点赞关系和点赞计数；
- 一级评论、楼中楼回复和评论计数；
- 热门推荐、好友动态和冷启动内容混排；
- 帖子详情两级缓存；
- 好友 Feed 异步写扩散；
- 点赞增量异步刷盘；
- 调用 user-service 获取用户资料。

一次请求通常经过：

```text
gRPC 接口层
  → Service 业务编排
  → Manager 领域数据访问
  → Mapper / Redis / RocketMQ / user-service
```

面试中应强调：接口层负责协议转换和基础校验，Service 负责事务及业务流程，Manager 封装数据访问和缓存细节。

### 2. Post Service 中哪些数据要求强一致，哪些允许最终一致？

| 数据 | 一致性策略 | 原因 |
| --- | --- | --- |
| 帖子、图片、初始统计 | PostgreSQL 本地事务 | 必须同时成功或失败 |
| 评论与评论数 | PostgreSQL 本地事务 | 评论频率相对低，适合强一致 |
| 点赞关系 | PostgreSQL 幂等写入 | 点赞关系是事实来源 |
| 点赞展示计数 | Redis 增量 + 定时刷盘 | 高频写入，允许短暂最终一致 |
| 帖子详情缓存 | Cache-Aside | 数据库是最终事实来源 |
| 好友 timeline | Outbox + RocketMQ | 异步扩散，允许最终一致 |

核心原则：

> 根据数据价值、写入频率和一致性要求选择方案，而不是让所有数据使用同一种架构。

## 二、帖子详情缓存

### 3. 为什么 `GetPostDetail` 需要缓存？

帖子详情是典型的读多写少数据。热门帖子可能被大量用户反复访问，如果每次直接查询 PostgreSQL，会增加：

- 数据库连接池压力；
- 索引和磁盘读取压力；
- 热点数据查询延迟；
- 数据库故障时的影响范围。

缓存可以降低数据库 QPS，并缩短详情接口响应时间。对于大型社交业务，还要考虑热门帖子形成的热点 Key 问题。

### 4. 为什么使用 Caffeine + Redis 两级缓存？

读取链路：

```text
请求
  → L1 Caffeine
  → L2 Redis
  → PostgreSQL
```

两层缓存的职责不同：

| 层级 | 配置 | 主要作用 |
| --- | --- | --- |
| Caffeine | 最多 50000 条，15 秒过期 | 吸收单实例内的热点请求，减少 Redis 网络访问 |
| Redis | 7 天 + 0～20 分钟随机抖动 | 多实例共享，保护 PostgreSQL |

Caffeine 不能替代 Redis，因为它不跨实例共享，服务重启后也会丢失；Redis 也不能完全替代 Caffeine，因为超热点帖子可能对单个 Redis Key 产生很高压力。

### 5. 为什么 Redis 缓存 7 天，而 Caffeine 只有 15 秒？

- 帖子正文、作者、图片等公共字段变化频率低，适合在 Redis 长时间缓存。
- Caffeine 的职责是吸收瞬时热点，不是长期保存业务数据。
- 多实例本地缓存存在一致性问题，短 TTL 可以限制失效消息漏收造成的陈旧窗口。
- 删除、封禁和修改帖子时仍需要主动失效缓存，7 天 TTL 只是兜底。

### 6. 为什么不把点赞数、评论数和 `isLiked` 放进帖子详情缓存？

详情缓存只保存低频变化的公共静态字段：

- postId；
- 作者；
- 正文；
- 状态；
- 图片；
- 创建时间。

动态字段单独查询：

```text
likeCount = DB 已刷盘值 + Redis 未刷盘增量
commentCount = DB 当前值
isLiked = 当前用户的点赞关系
```

原因：

- 点赞数变化频繁，放进正文缓存会导致频繁更新或删除整条缓存。
- `isLiked` 与当前登录用户有关，不能作为所有用户共享的缓存字段。
- 动静分离可以减少缓存写入、缓存失效和数据串用户问题。

### 7. 什么是 Cache-Aside？

当前详情缓存采用 Cache-Aside：

```text
读取：
查缓存
  → 未命中查数据库
  → 回填缓存

写入：
先提交数据库
  → 事务提交后更新或删除缓存
```

数据库始终是最终事实来源，缓存可以被删除并重新构建。

常见追问：为什么不先删除缓存再更新数据库？

如果先删缓存，另一个请求可能在数据库更新前回源，读取旧数据并重新写入缓存。数据库提交后再失效缓存更稳妥，但仍要处理删除缓存失败的问题。

### 8. 如何处理缓存穿透？

查询不存在的 postId 时写入负缓存：

```text
found=false
TTL=30秒
```

这样可以避免恶意或异常请求持续访问数据库。负缓存不能设置得太长，否则数据恢复或新数据写入后可能长时间不可见。

### 9. 如何处理缓存击穿？

热门帖子缓存失效时，同一个 postId 通过分布式锁限制并发回源：

```text
缓存未命中
  → 获取 postId 维度的 Redisson 锁
  → 再次检查缓存
  → 一个请求查询数据库并回填
  → 其他请求等待或重新读取缓存
```

关键点：

- 锁必须按 postId 粒度，不能锁住整个详情服务。
- 获取锁后必须二次检查缓存。
- 锁等待时间和租约不能太长。
- Redis 或 Redisson 故障时允许降级访问数据库。

### 10. 如何处理缓存雪崩？

当前正常详情 TTL 为：

```text
7天 + 0～20分钟随机抖动
```

随机抖动可以避免同一批帖子同时失效。此外，生产环境还应结合：

- 缓存预热；
- 请求限流；
- 熔断降级；
- 数据库连接池保护；
- 热点 Key 监控。

### 11. 多实例 Caffeine 如何失效？

删除或修改帖子时：

```text
删除当前实例 Caffeine
  → 删除 Redis 详情
  → Redis Pub/Sub 广播 postId
  → 其他实例删除本地 Caffeine
```

Redis Pub/Sub 不持久化消息，实例断线时可能漏收。因此：

- Caffeine 只缓存 15 秒；
- 短 TTL 是最终兜底；
- 如果封禁、隐私修改要求接近零陈旧，应使用可靠失效消息或缓存版本号。

### 12. Redis 故障时详情接口如何降级？

推荐链路：

```text
Caffeine 命中
  → 正常返回

Caffeine 未命中且 Redis 故障
  → 降级查询 PostgreSQL
```

缓存故障不能直接变成接口不可用，但必须配合数据库限流、超时、熔断和连接池隔离，防止全部流量同时回源压垮数据库。

## 三、数据库事务

### 13. 为什么创建帖子需要本地事务？

一次发帖涉及：

- `posts`；
- `post_images`；
- `post_stats`；
- `post_fanout_outbox`。

它们必须在同一个 PostgreSQL 事务中提交：

```text
BEGIN
  INSERT posts
  INSERT post_images
  INSERT post_stats
  INSERT post_fanout_outbox
COMMIT
```

否则可能出现帖子存在但图片或统计缺失，或者帖子成功但永远没有好友扩散事件。

### 14. 为什么 Redis 操作不能放在数据库事务中？

如果数据库提交前先写 Redis：

```text
Redis 写入成功
数据库事务回滚
```

Redis 中会出现数据库不存在的数据。

正确方式是：

```text
数据库事务提交成功
  → 再写缓存、冷启动池或发送失效通知
```

Redis 和 PostgreSQL 不属于同一个本地事务，不应该假装它们可以共同回滚。

### 15. Spring `@Transactional` 自调用为什么会失效？

典型错误：

```java
public void createPost() {
    this.saveInTransaction();
}

@Transactional
public void saveInTransaction() {
}
```

同一个对象内部调用不会经过 Spring AOP 代理，事务增强可能不生效。

常见解决办法：

- 把 `@Transactional` 放在被外部 Bean 调用的 public 方法上；
- 将事务方法拆到另一个 Spring Bean；
- 不通过 `this` 调用事务方法。

## 四、点赞与计数

### 16. 点赞接口如何保证幂等？

重复点赞不能重复增加计数。当前使用 PostgreSQL UPSERT，根据影响行数判断点赞状态是否真实变化：

```text
affected=1
  → 状态发生变化
  → Redis 点赞增量 ±1

affected=0
  → 重复请求
  → 不改变计数
```

相比“先查询再写入”，UPSERT 可以避免并发竞态：

```text
请求1查询：未点赞
请求2查询：未点赞
请求1计数+1
请求2计数+1
```

数据库唯一约束和原子 UPSERT 才是可靠的幂等基础。

### 17. 为什么点赞数采用 Redis 写合并？

热门帖子可能在短时间收到大量点赞。如果每次都更新 `post_stats`：

- 同一统计行成为热点行；
- 行锁竞争严重；
- 数据库产生大量 UPDATE 和 WAL；
- 写入吞吐下降。

当前策略：

```text
点赞关系立即写 PostgreSQL
  → 点赞增量写 Redis
  → 每分钟批量刷回 post_stats
```

读取时：

```text
likeCount = DB 基准值 + Redis 未刷盘增量
```

这是一种以短暂最终一致换取高吞吐的设计。

### 18. Lua 脚本解决了什么问题？

一次点赞需要同时执行：

```text
INCRBY likeDelta ±1
EXPIRE likeDelta 7天
SADD likeUpdatedSet postId
```

分多次执行时，中间失败可能导致：

- 有增量但没有 dirty 标记，后台任务找不到它；
- 有 dirty 标记但增量不存在；
- TTL 没有设置，Key 长期残留。

Lua 可以保证这一组 Redis 操作在 Redis 内原子执行。

### 19. 点赞增量刷盘会不会丢数据？

当前流程大致为：

```text
Lua 获取并清零 delta
  → 更新 PostgreSQL
  → 删除 dirty 标记
```

数据库更新失败时，当前进程会把 delta 加回 Redis。但如果进程在“Redis 清零后、数据库更新前”被强杀，仍存在一个极小的数据丢失窗口。

回答重点：

- 点赞关系表是事实来源。
- 点赞数是展示型最终一致数据，不是余额或库存。
- 生产环境应周期性从 `post_likes` 对账或离线重算。
- 强一致资金数据不能直接采用这种刷盘方案。

## 五、评论设计

### 20. 为什么评论数不使用 Redis 写合并？

评论频率通常低于点赞，因此评论创建和评论数更新可以放在同一个 PostgreSQL 事务：

```text
BEGIN
  INSERT post_comments
  UPDATE post_stats
    SET comment_count = comment_count + 1
COMMIT
```

优势：

- 评论记录与评论数保持一致；
- 不需要评论增量 dirty set；
- 不需要 `CommentFlushJob`；
- 架构更加简单。

重要的设计观点：

> 点赞适合 Redis 写合并，不代表所有计数都应该使用 Redis。

### 21. 楼中楼回复需要校验什么？

创建回复时至少要检查：

- 根评论是否存在；
- 父评论是否存在；
- 根评论和父评论是否属于当前帖子；
- 父评论是否处于同一个评论线程；
- `rootId`、`parentId` 和 `replyToUserId` 是否正确；
- 不允许跨帖子回复。

### 22. 为什么评论列表只缓存一级评论？

一级评论接口只应该返回 `rootId=0` 的评论。如果回复也写入同一个 Redis 窗口：

- Redis 路径和数据库路径的结果口径不同；
- 回复可能占满一级评论窗口；
- 页数、游标和 `hasMore` 会发生错误。

当前策略：

- 只缓存最近 200 条一级评论；
- 回复按照 rootId 单独查询；
- Redis 数据不足时回源数据库。

## 六、分页与批量查询

### 23. 为什么游标分页查询 `pageSize + 1` 条？

例如客户端请求 20 条，服务查询 21 条：

```text
查询结果 <= 20
  → hasMore=false

查询结果 = 21
  → 返回前20条
  → hasMore=true
  → 下一页游标取第20条
```

这样不需要额外执行一次 COUNT 查询。

### 24. 为什么 Feed 不适合 offset 分页？

Feed 数据持续新增和变化。使用：

```sql
LIMIT 20 OFFSET 1000
```

容易出现：

- 新数据插入导致重复；
- 删除数据导致漏读；
- OFFSET 越大，数据库扫描成本越高。

Feed 更适合基于时间或 score 的游标分页：

```text
score < lastScore
```

### 25. 如何解决 N+1 查询？

错误方式：

```text
查询20条帖子
  → 每条查询图片
  → 每条查询统计
  → 每条查询点赞关系
```

优化后：

```text
1次批量查询帖子
1次批量查询图片
1次批量查询统计
1次 Redis MGET 点赞增量
1次批量查询当前用户的点赞关系
```

面试中应提到：

- SQL `IN (...)` 批量查询；
- 按 postId 分组；
- Redis MGET；
- 批量 RPC；
- 避免循环内访问数据库或远程服务。

## 七、推荐 Feed

### 26. Feed 有哪些候选来源？

当前包含三路来源：

| 来源 | 作用 |
| --- | --- |
| 热门推荐池 | 提供高质量和高互动内容 |
| 好友 timeline | 保证社交关系内容出现 |
| 冷启动池 | 给新帖子基础曝光机会 |

三路内容需要进行混排、去重、批量组装和游标推进。

### 27. 什么是真正的位置混排？

例如规则是：

```text
每10条内容：
第3个位置放好友内容
第6个位置放冷启动内容
其他位置放热门推荐
```

错误方式是先连续加入热门内容，再尝试插入好友或冷启动内容，此时目标位置可能已经被占满。

正确方式是按照当前结果位置逐个选择候选来源。指定来源为空时还需要使用其他来源补位，避免一页数量不足。

### 28. Bloom Filter 在 Feed 中有什么作用？

Bloom Filter 用于记录用户最近已经看过的 postId，减少重复推荐。

当前需要关注：

- 容量 5000；
- 误判率 1%；
- TTL 7 天。

Bloom Filter 特点：

- 可能把没看过的内容误判为看过；
- 不会把已经存在的数据判断为一定不存在；
- 普通 Bloom Filter 不支持精确删除单个元素；
- 适合 Feed 去重，不适合作为精确业务事实来源；
- 容量估计不足时误判率会快速上升。

### 29. 冷启动池解决什么问题？

新帖子缺少点赞、评论等行为数据，正常排序分数低，很难进入热门推荐。

冷启动池负责：

- 按用户属性分桶；
- 保留最近一定数量的新帖；
- 设置 TTL；
- 在 Feed 固定位置给予曝光；
- 收集互动数据后进入正常推荐逻辑。

### 30. Feed 分数通常如何设计？

常见因素包括：

- 点赞数；
- 评论数；
- 发布时间；
- 时间衰减；
- 作者属性；
- 内容质量；
- 举报和风控状态；
- 用户兴趣匹配。

基本思路：

```text
score = 互动权重 + 内容质量 - 时间衰减
```

没有时间衰减时，历史热门帖子可能长期占据推荐池。

## 八、写扩散与读扩散

### 31. 什么是写扩散？

写扩散也叫 Fan-out on Write。作者发帖后，将 postId 异步写入每个好友的 timeline：

```text
A发布 post-100
  → 写入B的timeline
  → 写入C的timeline
  → 写入D的timeline
```

这里只扩散 postId，不复制完整帖子正文。

优点：

- Feed 读取快；
- 游标分页简单；
- 适合读多写少的普通社交用户。

缺点：

- 发帖产生写放大；
- 大 V 会造成写入风暴；
- timeline 存储量更大。

### 32. 什么是读扩散？

读扩散也叫 Fan-out on Read。发帖时只保存帖子，用户请求 Feed 时再查询所有关注作者的最近帖子并现场归并：

```text
B请求Feed
  → 查询好友列表
  → 查询每个好友的最近帖子
  → 合并、去重、排序和分页
```

优点：

- 发帖成本低；
- 不需要为所有粉丝提前写 timeline；
- 适合粉丝数特别大的作者。

缺点：

- Feed 读取复杂；
- 多路游标和排序困难；
- 延迟受好友数量影响。

### 33. 为什么当前服务采用写扩散？

原因：

- Feed 读取次数通常远高于发帖次数；
- 普通用户的好友数量相对可控；
- 写扩散可以把高频 Feed 请求简化成读取一个 Redis ZSet；
- 好友内容可以直接参与位置混排；
- RocketMQ 把 O(N) 扩散从发帖主链路中剥离。

### 34. 陌陌体量的业务应该只使用写扩散吗？

不应该一刀切。大型社交平台通常使用混合扩散：

```text
普通用户
  → 写扩散

大 V / 主播 / 公众账号
  → 读扩散

中等规模账号
  → 只向近期活跃用户写扩散
  → 非活跃用户读取时补偿
```

具体阈值应根据 MQ 吞吐、Redis 写入能力、用户活跃度和 Feed 延迟压测确定，不能直接写死。

## 九、RocketMQ 与 Transactional Outbox

### 35. 为什么好友扩散需要 MQ？

一个作者可能有大量好友，如果发帖接口同步遍历：

- 发帖延迟与好友数量相关；
- user-service 或 Redis 抖动会拖累发帖；
- 请求容易超时；
- 失败后难以重试。

异步流程：

```text
发帖成功
  → RocketMQ
  → Consumer 查询好友
  → 批量写入好友 timeline
```

MQ 的价值是异步解耦和削峰，不是用来装饰架构。

### 36. 为什么直接发送 RocketMQ 还不够？

存在数据库和 MQ 双写不一致：

```text
数据库提交成功
MQ发送失败
  → 帖子存在，但好友永远收不到
```

如果先发 MQ：

```text
MQ发送成功
数据库事务回滚
  → Consumer 处理一个不存在的帖子
```

### 37. Transactional Outbox 是什么？

在发帖的本地数据库事务中同时插入 Outbox：

```text
BEGIN
  INSERT posts
  INSERT post_fanout_outbox(status=PENDING)
COMMIT
```

后台任务每隔一段时间扫描：

```text
PENDING
  → 发送 RocketMQ
  → 成功后标记 DELIVERED
  → 失败后更新 next_retry_at
```

只要数据库事务成功，扩散事件就不会悄悄丢失。

### 38. Outbox 能保证消息恰好投递一次吗？

通常只能保证至少一次投递。

可能出现：

```text
MQ发送成功
更新Outbox状态前进程崩溃
  → 后台任务再次发送
```

因此 Consumer 必须幂等，不能依赖“消息绝对只来一次”。

### 39. Consumer 如何保证幂等？

好友 timeline 使用 Redis ZSet，并以 postId 作为 member：

```text
ZADD timeline score postId
```

同一个 postId 重复消费，只会更新同一个 member，不会产生多条重复记录。这是利用存储结构实现业务幂等。

### 40. 为什么没有使用延时消息？

当前业务没有：

- 定时发布；
- 预约提醒；
- 等待未来时刻自动曝光。

Outbox 失败重试使用：

```text
next_retry_at + 定时扫描
```

它具备可查询、可监控、可补单的优点，所以没有必要为了重试额外引入 RocketMQ 延时消息。

### 41. Outbox 需要监控什么？

至少包括：

- PENDING 事件数量；
- 最老 PENDING 事件年龄；
- 每分钟新增量和投递成功量；
- 平均重试次数；
- 投递失败率；
- RocketMQ Consumer Lag；
- timeline Redis 写入失败率；
- DELIVERED 历史数据清理情况。

## 十、微服务调用

### 42. gRPC Channel 为什么应该复用？

每次请求创建 Channel 会产生：

- TCP 和 HTTP/2 建连成本；
- TLS 握手成本；
- 连接数量失控；
- 资源泄漏风险；
- 更高的接口延迟。

正确方式：

- Channel 作为 Spring 单例 Bean；
- Stub 复用 Channel；
- 应用关闭时统一 shutdown；
- 配置合理的 deadline、重试和熔断。

### 43. 用户性别为什么也使用两级缓存？

Feed 分桶和冷启动池需要用户属性：

```text
Caffeine 30秒
  → Redis 6小时
  → user-service Profile RPC
```

这样可以减少远程调用，同时允许用户资料修改后在有限时间内生效。

常见追问：

- 空值是否缓存；
- RPC 超时如何降级；
- Redis 故障时是否直接调用 user-service；
- 如何使用批量 RPC 避免逐用户调用；
- 用户资料变化如何主动失效缓存。

### 44. 为什么 post-service 不应该直接查询 user-service 数据库？

直接跨库查询会：

- 破坏微服务边界；
- 耦合对方数据库结构；
- 绕过 user-service 业务规则；
- 增加权限和部署复杂度；
- 阻碍服务独立演进。

应通过正式的好友/关注 RPC 或领域事件获取关系数据。

当前项目的生产边界是：`user.proto` 已提供 Profile RPC，但缺少好友列表 RPC，因此好友写扩散架构已经完成，Consumer 暂时还无法获取真实好友列表。

## 十一、生产稳定性与监控

### 45. 缓存需要监控哪些指标？

- Caffeine 命中率；
- Redis 命中率；
- PostgreSQL 回源率；
- 热点 Key QPS；
- Redis P95/P99 延迟；
- 分布式锁获取失败率；
- 负缓存命中率；
- 缓存序列化和反序列化失败；
- Pub/Sub 失效消息处理情况；
- 单个 postId 的异常流量。

### 46. 数据库需要关注什么？

- 慢 SQL；
- 连接池使用率；
- 热点统计行锁竞争；
- 查询是否命中索引；
- 大量 `IN` 查询的批次大小；
- 事务持续时间；
- 死锁和回滚率；
- 点赞刷盘批次耗时。

### 47. Feed 需要关注什么？

- Feed 请求 P95/P99；
- 三路候选池命中情况；
- 一页实际返回数量；
- Bloom Filter 误判率；
- 重复内容比例；
- 冷启动内容曝光量；
- 好友内容占比；
- Redis ZSet 大小；
- 推荐池重建耗时和失败率。

### 48. 如何进行容量估算？

面试中可以从以下维度估算：

```text
每日发帖量
× 平均帖子缓存大小
× 缓存7天
```

写扩散容量：

```text
每日发帖量
× 平均好友数
× 活跃用户比例
× timeline保留条数
```

MQ 吞吐：

```text
峰值发帖QPS
× 平均好友数
```

还应考虑：

- Redis 主从和集群副本开销；
- JSON 序列化额外空间；
- Key 本身占用；
- 大 V 极端流量；
- 重试造成的额外消息量。

## 十三、推荐回答结构

面对设计类问题，可以按下面的顺序回答：

```text
1. 先说明业务和数据特征
2. 再说明当前方案
3. 解释为什么选择这个方案
4. 说明一致性和失败处理
5. 指出方案的边界
6. 给出大规模场景下的演进方式
```

例如回答“为什么使用两级缓存”：

```text
帖子详情读多写少，并且热门帖子存在热点访问，所以使用缓存保护数据库。
Redis 作为多实例共享的 L2 缓存，缓存7天；Caffeine 作为15秒的 L1 缓存，
用于吸收单实例热点并减少 Redis 网络访问。缓存只保存公共静态字段，
点赞数和 isLiked 动态组装。缓存未命中时通过 postId 粒度分布式锁防击穿，
不存在的数据负缓存30秒防穿透，Redis TTL 增加随机抖动防雪崩。
删除帖子时主动失效 Redis，并通过 Pub/Sub 清理其他实例的 Caffeine；
即使漏收，本地缓存也会在15秒内过期。
```

一个完整回答应同时覆盖“为什么这样做”和“这样做还有什么问题”，而不是只罗列技术名词。
