# Post Service 业务流程详解

> 本文用业务语言解释 2026-07-29 优化后的 post-service。

## 一、服务定位

Post Service 负责约会 App 中一条动态从产生到分发、互动和删除的完整生命周期：

1. 用户发布文本和图片动态。
2. 系统保存帖子，并把“需要向好友扩散”这件事可靠记下来。
3. 新帖进入冷启动池，后台计算热门池。
4. 用户从个人主页或综合 Feed 查看内容。
5. 用户点赞、评论或删除自己的内容。
6. 后台把高频点赞计数从 Redis 合并回 PostgreSQL。

图片文件不保存在本服务，post-service 只保存对象存储 key。

---

## 二、发布与删除

### 2.1 发布帖子

发帖时，`posts`、`post_images`、`post_stats` 和 `post_fanout_outbox` 在同一个 PostgreSQL 事务中提交：

```text
帖子主记录
+ 图片引用
+ 初始统计
+ 好友扩散承诺
```

任何一步失败，四部分一起回滚。原来三张业务表的事务注解放在内部方法上，可能因 Spring 自调用而失效；现在事务边界放到了实际被 gRPC 调用的 public 方法上。

数据库提交以后才更新缓存和冷启动池。这样即使 Redis 暂时不可用，也不会让数据库中的帖子跟着回滚。

新帖冷启动池按作者性别分桶，只保留最近 10000 条并设置 7 天 TTL。

### 2.2 删除帖子

只有作者能删除自己的帖子。数据库把帖子逻辑删除并移除图片引用，提交后再：

- 删除 Redis 详情；
- 删除当前实例 Caffeine；
- 广播其他实例删除本地 Caffeine；
- 从冷启动池移除。

其他实例即使漏掉 Redis 广播，Caffeine 也会在 15 秒内过期。

---

## 三、帖子详情为什么使用两级缓存

帖子正文、图片和作者信息读多写少，热门帖子可能被大量用户反复打开；但点赞数和“我是否点赞”变化频繁。

因此没有缓存整个响应，而是拆成：

```text
公共详情：
  Caffeine → Redis → PostgreSQL

实时计数：
  DB 基准 + Redis 点赞增量

用户状态：
  单独查询 post_likes
```

### 3.1 Caffeine

- 每个服务实例最多 50000 条；
- 15 秒过期；
- 目的只是挡住同一实例对 Redis 热点 key 的重复访问。

### 3.2 Redis

- key 使用版本号：`putao:post:detail:v1:<postId>`；
- 正常详情缓存 7 天，并增加最多 20 分钟随机抖动；
- 不存在的帖子缓存 30 秒，防止缓存穿透。

### 3.3 热点保护

两级缓存都没有时，同一个 postId 通过 Redisson 分布式锁限制并发回源。其他请求等待最多 200ms，然后重新检查缓存。

Redis 或 Redisson 故障时，服务允许回源 PostgreSQL，不会因为缓存故障直接让详情接口不可用。

### 3.4 为什么计数不放进详情缓存

如果点赞数也放在正文缓存里，每次点赞都要更新或删除整条详情，热门帖会产生大量缓存写入。

现在只缓存低频变化部分：

```text
likeCount = DB 已刷盘值 + Redis 未刷盘值
commentCount = DB 当前值
isLiked = 当前用户的点赞关系
```

## 四、个人主页列表

用户帖子列表用雪花 `post_id` 做游标，服务多取一条判断是否还有下一页。

之前每条帖子分别查图片和统计，一页 N 条会产生明显的 N+1 查询。现在一页统一批量查询：

- 帖子；
- 图片；
- DB 统计；
- Redis 点赞增量；
- 当前用户的点赞状态。

页大小限制为最多 50 条，避免调用方用异常参数放大数据库压力。

---

## 五、点赞与评论为什么采用不同的计数策略

### 5.1 点赞：Redis 写合并

点赞频率通常高于评论，因此保留 Redis 写合并：

1. PostgreSQL UPSERT 点赞关系；
2. 只有关系状态真实变化时才更新计数；
3. Lua 原子完成 `INCRBY + EXPIRE + SADD dirty set`；
4. 读取时返回 DB 基准加 Redis 增量；
5. 每分钟批量刷回 `post_stats`。

旧实现先查再 UPSERT，两个并发点赞可能都给 Redis 加一；现在直接使用 PostgreSQL 影响行数判断是否发生变化。

刷盘失败时会把 delta 加回 Redis。由于 Redis 和 PostgreSQL 之间没有分布式事务，进程在极窄窗口被强杀仍可能造成展示计数偏差，生产上应周期性用 `post_likes` 对账。展示计数不属于扣费数据，因此没有为它额外引入 MQ。

### 5.2 评论：本地事务强一致

评论量相对较低，评论记录和评论数直接在一个 PostgreSQL 事务中更新：

```text
INSERT/DELETE comment
+ comment_count ±1
```

这让评论不再需要 Redis delta，也删除了 `CommentFlushJob`，彻底避免点赞 Job 和评论 Job 争抢同一个 dirty set。

评论回复会校验根评论、父评论和帖子是否属于同一线程，并自动填充 `replyToUserId`。

评论列表只缓存最近 200 条一级评论；回复不会混进一级评论接口。Redis 不足时回源 DB，两条路径口径一致。

删除评论已经改成按业务 `comment_id` 查询，不再把它错误当作内部自增主键。

## 六、推荐 Feed

综合 Feed 由三路内容组成：

| 来源 | 作用 |
| --- | --- |
| 热门池 | 提供近期高互动内容 |
| 好友 timeline | 保证社交关系内容出现 |
| 冷启动池 | 给新帖曝光机会 |

每 10 个位置计划为：

```text
8 个热门
第 3 个好友
第 6 个冷启动
```

旧实现先把热门内容连续追加，好友位和冷启动位通常已经被占用。现在先按位置选择候选，再批量读取详情；指定来源为空时由热门、冷启动或好友内容依次补位。

BloomFilter 保存用户看过的 postId：

- 容量 5000；
- 误判率 1%；
- TTL 7 天。

Feed 的帖子、图片、统计和点赞状态全部批量查询，不再逐帖回数据库。

热门池每 5 分钟重建一次。系统读取近 3 天帖子，按点赞、评论和时间衰减计算分数，按作者性别分桶，各保留 Top 3000，再通过临时 ZSet 和 `RENAME` 替换正式池。

用户性别现在使用：

```text
Caffeine 30秒 → Redis 6小时 → user-service Profile RPC
```

不再用 userId 奇偶数模拟，也不再为每次调用创建新的 gRPC Channel。

## 七、为什么好友扩散需要 MQ

一个作者发帖后，可能需要把 postId 写入很多好友的 timeline。如果在发帖请求中同步循环：

- 好友越多，发帖越慢；
- user-service 或 Redis 抖动会拖累发帖；
- 请求超时后重试容易重复写。

所以好友扩散继续使用 RocketMQ。

### 7.1 为什么增加 Outbox

只在数据库提交后直接发 MQ，会存在：

```text
帖子 COMMIT
  → 进程崩溃
  → MQ 没发送
```

现在发帖事务同时插入 `post_fanout_outbox`。后台每 5 秒扫描 PENDING 事件：

- Producer 本地重试 3 次；
- 仍失败则记录 attempts，并按指数退避重试；
- 最长退避 5 分钟；
- 成功后标记 DELIVERED；
- 7 天后由清理 Job 分批删除。

Consumer 对 timeline 使用 postId 做 ZSet member，重复消息只会覆盖同一 member，因此 Outbox 的至少一次投递是安全的。

### 7.2 为什么不使用延时消息

当前没有定时发布、预约提醒或等待未来时刻执行的业务。Outbox 重试通过数据库 `next_retry_at` 完成，可查询、可补单、可监控，所以没有引入 RocketMQ 延时消息。

## 八、当前未完成的外部依赖

`user.proto` 已提供用户 Profile，但还没有好友/关注列表 RPC。因此：

- 性别分桶已接真实 user-service；
- 好友写扩散架构和可靠投递已完成；
- Consumer 暂时取不到好友，好友 timeline 仍为空；
- 热门池和冷启动池不受影响。

下一步应先在 user-service 提供正式好友列表接口，再启用真实 fanout，而不是在 post-service 跨库读取关系数据。

## 九、优化后的关键取舍

| 场景 | 方案 | 原因 |
| --- | --- | --- |
| 热门详情 | Caffeine + Redis Cache-Aside | 同时保护 Redis 和 DB |
| 不存在帖子 | Redis 负缓存 | 防穿透 |
| 热点过期 | 分布式单飞 + TTL 抖动 | 防击穿和雪崩 |
| 点赞计数 | Redis 写合并 | 高频、允许最终一致 |
| 评论计数 | DB 本地事务 | 频率较低，简化一致性 |
| 好友扩散 | Outbox + RocketMQ | O(N) 异步任务，需要可靠投递 |
| Outbox 重试 | DB next_retry_at | 可查、可补单，无需延时消息 |
| Feed 详情 | 批量查询 | 消除 N+1 |

## 十、一句话总结

优化后的 Post Service 把不同数据按特性拆开处理：公共详情使用两级缓存，点赞使用 Redis 写合并，评论使用数据库事务，好友扩散使用 Outbox + RocketMQ，Feed 使用真正的位置混排和批量组装。消息队列只用于确实需要异步削峰的好友扩散，没有为了“架构看起来复杂”而加入延时消息。
