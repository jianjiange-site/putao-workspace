# Match Service 业务流程详解

## 一、概述

Match Service 是约会交友 App 的核心服务，负责"用户匹配"这条主线：从推荐卡片、划卡互动、到配对成功、以及后续的访客/点赞通知等。整体设计围绕两条核心链路：**推荐与划卡**（用户看见别人、产生互动）和**匹配后通知**（配对成功后的 IM 会话、系统消息、数字人开场白）。

---

## 二、推荐卡片流

### 2.1 拉取今日 Feed

当用户打开 App 准备划卡时，系统会从 Redis 队列中取出推荐卡片返回给前端。

**流程如下：**

1. **配额校验**：先查用户今天还能划多少张卡。如果配额耗尽，直接返回空列表并标记 `exhausted=true`。

2. **从 Redis 队列取卡片**：用户的推荐卡片存在 Redis LIST 里，key 是 `putao:match:feed:<userId>`。系统用 `LPOP` 依次取出，默认一次取 5 张。

3. **二次过滤已划过的人**：卡片队列是异步构建的，用户可能在之前划过但队列还没更新。因此会用 Redis SET `match:swiped:<userId>` 检查，把已划过的人过滤掉。

4. **补卡机制**：如果一轮取不够 5 张，会继续循环拉取，最多 8 轮。如果队列空了（说明用户是首次或队列耗尽），会触发**冷启动重建**重新生成推荐。

5. **组装用户资料**：把卡片上的目标用户 ID 批量调 user-service 拿昵称、年龄、头像等信息，然后返回给前端。

### 2.2 冷启动召回（新用户首登或队列为空）

当用户的推荐队列为空时，系统会实时为用户生成一批推荐卡片，这个过程叫做"冷启动"。

**核心逻辑：**

1. **取用户画像**：从 user-service 拿当前用户的性别、年龄、位置、人种等信息。缺字段给默认值（年龄缺则 25）。

2. **排除已划过的人**：查历史划卡记录，把滑过的人排除，避免重复推荐。

3. **双池召回**：系统有两类用户池——BH（普通新用户池）和 DH（延迟匹配池，AI 数字人）。
   - **BH 池**：严格条件筛选（距离 100km 内、年龄 ±5 岁、颜值 ±15、7 天内有活跃），直接拉取。
   - **DH 池**：渐进扩范围。先用最严格条件（L0：同龄同人种），不够就放宽到 L1（放开人种）、L2（放宽年龄颜值）、L3（兜底）。这样保证"能匹配上的优先推，不够再扩大范围"。

4. **排序合并**：BH 按新用户优先 + 同人种 + 年龄接近 + 颜值高排序；DH 按同人种 + 年龄接近 + 颜值高排序。然后按 20% BH + 80% DH 的比例混合。

5. **写入 Redis**：用 RPUSH 把混合后的 240 张卡片写入用户队列，TTL 设置 7 天。

> **设计意图**：BH 是新用户、需要被看到，DH 是 AI 数字人、需要提升活跃度。混合推送既保证新用户有机会被匹配，又能让 AI 数字人穿插其中增加互动趣味。

### 2.3 D1 日更离线生成（每日更新个性化推荐）

每天凌晨（美东 03:00，对应 UTC 07:00），定时任务会离线计算所有用户的个性化推荐队列，用最新的数据覆盖 Redis 中的队列。

与 D0 冷启动的区别：
- D0 是**追加**（RPUSH），用于兜底补偿
- D1 是**覆盖**（DEL + RPUSH），用当天最新的召回结果

## 三、划卡与 Super Hi

### 3.1 普通划卡（Swipe）

用户对一张卡片执行左滑（不感兴趣）或右滑（喜欢）的操作。

**流程：**

1. **幂等检查**：用分布式锁 `lock:match:swipe:<userId>:<targetUserId>` 防止并发重复划同一张卡。如果已划过，直接返回历史结果（不扣配额）。

2. **配额扣减**：
   - 左滑：扣每日可划卡片数
   - 右滑：扣每日可划卡片数 + 扣每日右划次数

3. **写历史 + 触发匹配**（同一事务）：
   - **左滑**：直接写入划卡历史表，返回。
   - **右滑 BH 用户**：先写历史，然后查对方是否也右滑了我。如果是双向右滑，立即创建 match；如果对方没回滑，则写入 like_record（暗恋记录）。
   - **右滑 DH 用户**：写历史后，不立即匹配，而是调度一个延迟任务（15秒~2分钟随机），等对方"回滑"后再创建 match。延迟的好处是：用户看到"配对成功"时，对面是个真实在线的 AI，有更好的互动体验。

4. **标记已划**：把目标用户 ID 写入 Redis SET `match:swiped:<userId>`，供 Feed 二次过滤。

### 3.2 Super Hi（付费强匹配）

Super Hi 是一种付费功能，用户可以无视条件硬匹配任意目标，无需对方回滑。

**与普通右滑的区别：**

| | 普通右滑 | Super Hi |
|---|---|---|
| 匹配条件 | 需要对方也右滑 | 直接匹配，无需对方同意 |
| BH 用户 | 查 reverse，双方右滑才匹配 | 立即匹配 |
| DH 用户 | 延迟匹配 | 立即匹配 |
| 费用 | 免费 | 订阅用户有免费次数，超出后扣金币 |

**配额扣减逻辑：**
- 先用订阅等级对应的免费次数
- 免费次数用完后，用金币购买（每个 Super Hi 消耗固定金币）

**事务边界**：写划卡历史 + 创建 match + 扣配额 + 扣金币（如果需要）在同一事务内。如果金币扣减失败，回滚配额，保证一致性。

### 3.3 查看匹配列表与配额

- **匹配列表**：查 match 表，返回所有配对成功的用户信息（昵称、头像、配对时间、配对来源）
- **配额快照**：查用户当前剩余的每日可划卡片数、右划次数、Super Hi 次数

## 四、访客与点赞通知

### 4.1 谁访问了我 / 谁喜欢了我

用户可以查看"谁访问了我的主页"和"谁点赞了我"的列表。

**实现逻辑（两个功能完全一致）：**

1. 从数据库查访客记录表或点赞记录表，按时间倒序取最新 N 条
2. 批量调 user-service 获取这些用户的昵称、头像等信息
3. 组装后返回给前端，支持游标分页

### 4.2 记录访问（RecordVisit）

当用户浏览他人主页时，需要记录这次访问。

**设计要点：**

1. **自我访问短路**：用户看自己的主页不算访问，直接返回，避免刷访问量。

2. **异步落库**：访问记录通过 Outbox 异步写入数据库，用户浏览主页时不会因为写库而卡顿。

3. **失败降级**：如果写库失败，记录日志但不影响主流程。前端收到 `ok=false` 但不会报错。

> **通用模式**：match-service 的写入路径统一采用"异步化 + 自我短路 + 降级不抛"的模式，既保证性能又不影响用户体验。

## 五、DH 水军系统（提升新用户活跃感知）

### 5.1 背景

新注册用户（BH）如果没有即时的互动，会感觉 App 不活跃，很快就流失。DH 水军系统的目的是：通过 AI 数字人（DH）模拟真实用户的互动行为（访问主页、点赞），给 BH 用户制造"有人在关注我"的感知。

### 5.2 在线场景（Online Plan）

当有 BH 用户正在活跃（在线并滑动卡片）时，系统每分钟"drip"一批 DH 互动。

**触发条件：**
- 目标用户必须是 BH
- BH 24 小时内收到 DH 互动次数未达上限
- 排除已划过该 DH 的用户

**执行时机**：在 `[now, now+1分钟]` 区间内随机安排执行时间，模拟"实时看到有人关注我"的体验。

### 5.3 离线场景（Offline Plan）

当 BH 用户离线超过 20 分钟后，系统每 20 分钟扫描一次，批量生成 DH 互动任务。

**触发条件**：同上，但冷却时间更长。

**执行时机**：在 `[now, now+20分钟]` 区间内随机安排。

### 5.4 任务执行（LikeVisitor Executor）

定时扫描 `dh_interaction_task` 表，执行到期的任务。

**任务类型：**
- `ACTION_LIKE`：写入 like_record 表，source 标记为 `DH_PLAN_ONLINE` 或 `DH_PLAN_OFFLINE`
- `ACTION_VISIT`：写入 visit_record 表，visit_count +1

**失败重试**：执行失败的任务留在表里，下一轮继续被扫描执行，直到成功才物理删除。

> **关键设计**：任务表是"短生命周期中间表"，执行完就删；失败不删 = 天然重试机制，无需 RocketMQ 等消息队列。

### 5.5 源标记

DH 模拟的互动在 `like_record` 和 `visit_record` 表里有 `source` 字段标记，前端可以据此加特殊徽章或过滤掉这些模拟互动，只展示真实用户的互动。

## 六、配对后的跨服务通知（Outbox 模式）

### 6.1 问题背景

配对成功（match）后，需要做一系列跨服务的事情：
- 在 IM 服务建立会话
- 给双方发"配对成功"的系统消息
- 如果对方是 AI 数字人（DH），还要触发 AI 生成开场白

如果这些事情都在创建 match 的事务里同步调用：
- 下游 IM 抖动会拖垮主事务
- IM 建会话失败会导致 match 事务回滚
- 发了部分消息失败会导致数据不一致

### 6.2 Outbox 解决方案

**核心思路**：把"业务结果"（match 落库）和"跨服务副作用"（IM 通知）物理上解耦。

**实现方式：**

1. **本地事务内写 outbox**：创建 match 时，在同一事务内写入 `match_outbox` 表，记录"待执行的副作用任务"（type=ENSURE_CONVERSATION、SYSTEM_MSG、DH_OPENING），包括调用的参数（JSON 序列化）。

2. **后台异步消费**：事务提交后，有两个触发点：
   - **热路径**：`MatchOutboxService.deliver()` 立即拉取 PENDING 记录去执行
   - **兜底**：`MatchOutboxRetry` 每 30 秒巡检一次，处理积压记录

3. **执行结果**：成功则更新 status=DELIVERED；失败则 attempts++，下次继续重试。

**保证：**
- outbox 和 match 同事务提交，要么一起落库，要么一起回滚
- JSON 序列化的 payload 兼容字段升级
- 重试机制保证最终一致性

> **一句话**：match_outbox 是 match 事务里的"承诺书"——承诺会去执行跨服务的副作用，用本地事务保证承诺一定被记下来，用异步重试保证承诺最终被执行。

### 6.3 DH 开场白的特殊处理

DH 开场白是 AI 模型生成首条消息，耗时 1~3 秒。如果同步调：
- 用户配对请求卡 3 秒才返回
- AI 服务挂了，match 事务回滚，用户白高兴

走 outbox 后：match 立刻返回，AI 慢慢生成，生成完再 IM 推送给用户。用户体验是"配对成功 → 弹系统消息 → 几秒后收到 DH 招呼"。

## 七、关键设计总结

| 场景 | 核心设计 | 解决的问题 |
|---|---|---|
| Feed 推荐队列 | Redis LIST + 二次过滤 | 高并发下快速拉取 + 避免重复推荐 |
| 冷启动召回 | DH 池渐进扩范围 + BH/DH 混合 | 新用户有推荐 + 优先推送高质量匹配 |
| 划卡幂等 | 分布式锁 + 数据库查重 | 并发重复划卡 |
| BH 互滑匹配 | 查 reverse + INSERT IGNORE | 双向确认后才匹配 |
| DH 延迟匹配 | schedule 延迟任务 | 制造"对方在线"的真实感 |
| Super Hi | 立即匹配 + 金币幂等扣减 | 付费强匹配 + 防止重复扣费 |
| 访问记录 | 异步落库 + 自我短路 | 不阻塞主流程 + 防刷访问量 |
| DH 水军 | 任务表 + 失败重试 | 模拟互动 + 零外部依赖 |
| 跨服务通知 | Outbox 模式 | 事务一致 + 下游抖动不影响主链路 |
