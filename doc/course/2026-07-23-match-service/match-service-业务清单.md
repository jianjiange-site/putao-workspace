# Match Service 业务清单

> 本文只描述用户能使用的功能、业务规则、交互流程和数据流转。技术调用链、字段结构、错误码和代码实现统一放在 `match-service-业务流程详解.md`。

## 一、模块定位与边界

Match Service 负责 Dating App 从“看到候选人”到“建立匹配关系”的完整链路：

- 为用户准备并消费首页推荐卡片；
- 处理左划、右划和 Super Hi；
- 判断真人互相喜欢或延迟创建数字人匹配；
- 保存 Match、单向 Like、主页 Visit 和划卡历史；
- 在匹配后可靠触发聊天会话、系统消息和数字人开场白；
- 维护每日配额、D0 冷启动、D1 日更推荐和数字人模拟互动计划。

服务边界：

| 数据/能力 | 归属 |
| --- | --- |
| 推荐队列、划卡、Match、Like、Visit、可靠任务 | Match Service |
| 用户资料、真人/数字人类型、候选召回 | user-service |
| 订阅档位、金币扣减 | payment-service |
| 在线/离线状态、会话、系统消息、数字人开场白 | im-service |

Match Service 不跨库读取其他服务的数据。当前没有接入 MQ；核心可靠异步流程使用 PostgreSQL 持久化任务和租约抢占。

## 二、用户角色

| 角色 | 行为 |
| --- | --- |
| 普通用户 | 浏览候选、左划、右划、Super Hi、查看匹配/喜欢/访问和配额 |
| 真人候选 BH | 被推荐、被喜欢、互划后即时匹配 |
| 数字人候选 DH | 被推荐、普通右划后延迟匹配、Super Hi 后立即匹配 |
| 后台系统 | 生成推荐、执行延迟匹配、投递 Match 副作用、恢复 Super Hi、生成 DH 互动 |

## 四、推荐与浏览

### F001 获取今日推荐

#### 功能描述

用户打开首页后获取一批候选卡片。候选由真人 BH 和数字人 DH 两个池组成，队列为空时系统会即时执行 D0 冷启动召回。

#### 业务规则

- 单次期望数量使用系统默认值，并受最大数量限制。
- 返回数量不能超过用户当日剩余 cards 配额。
- 拉取卡片本身不扣配额，真正左划、右划或 Super Hi 时才扣。
- 已经划过的目标不能再次返回。
- 卡片队列只保存目标 ID 和用户类型，展示资料由 user-service 补齐。
- DH 距离固定使用不可用值；当前 BH 距离没有在本服务计算。
- 队列和配额都为空时均可能表现为“今日已看完”。

#### 用户交互流程

```text
打开首页
  → 系统检查订阅档位和剩余 cards
  → 从个人推荐队列取卡片
  → 过滤已划过目标
  → 队列为空时同步生成 D0 推荐
  → 批量补齐昵称、年龄、头像和简介
  → 展示卡片或今日已看完
```

#### 数据流转

```text
订阅档位 + Redis 配额
  → Redis Feed LIST
  → Redis swiped SET 二次过滤
  → user-service 批量资料
  → 首页卡片
```

#### 当前边界

- Redis LIST 中弹出的卡片即被消费，即使资料查询失败也不会放回。
- 同一用户没有队列重建 single-flight，并发空队列请求可能重复追加。
- 当前逐个检查已划状态，候选增多时 Redis 往返会放大。
- 脏格式卡片可能造成目标 ID 和类型下标错位。

### D0 冷启动支持流程

当队列为空时：

1. 读取当前用户画像。
2. 计算目标性别、年龄中心和默认颜值中心。
3. 从权威划卡历史得到排除列表。
4. 分别召回 DH 和 BH 候选。
5. 两个池独立排序。
6. 按 D0 比例合并和去重。
7. 追加写入个人 Redis Feed LIST，并设置 TTL。

画像缺失或没有候选时不会写入卡片。

## 五、划卡和匹配

### F002 普通划卡

#### 功能描述

用户对当前卡片左划或右划。左划表示跳过；右划真人表示喜欢，双方互相喜欢时立即匹配；右划数字人会在 15 秒到 2 分钟后尝试匹配。

#### 业务规则

- 不能对自己划卡。
- 只接受左划或右划。
- 同一用户和目标的重复请求幂等，不重复扣配额。
- 左划消耗一张 cards。
- 右划同时消耗一张 cards 和一次 right swipe。
- 配额检查和增加必须原子完成。
- 划卡历史是权威事实，Redis swiped SET 只是过滤缓存。
- 真人互划产生一个唯一 Match。
- 数字人普通右划不立即返回 Match。

#### 用户交互流程

```text
左划或右划
  → 系统串行化同一用户-目标操作
  → 重复请求直接复用历史结果
  → 确认目标真人/数字人类型
  → 原子预扣当日配额
  → 事务保存划卡
  → 按 LEFT / BH RIGHT / DH RIGHT 分支处理
  → 事务失败归还配额
  → 成功后更新已划缓存
```

#### 左划数据流

```text
Redis cards +1
  → PostgreSQL 划卡历史 LEFT
  → Redis swiped SET
```

#### 右划真人数据流

```text
Redis cards/right +1
  → PostgreSQL 划卡历史 RIGHT
  → 对方尚未喜欢：保存单向 Like
  → 对方已经喜欢：创建 Match、清理 Like、写 Outbox
```

#### 右划数字人数据流

```text
Redis cards/right +1
  → PostgreSQL 划卡历史 RIGHT
  → 同事务写入延迟匹配任务
  → 请求先返回未匹配
  → 后台到期后再次确认 DH 类型并创建 Match
```

### F003 Super Hi

#### 功能描述

Super Hi 跳过普通互划条件，对真人或数字人都立即建立 Match。用户优先使用订阅赠送额度，额度不足时使用金币。

#### 业务规则

- 不能对自己使用。
- 与普通 Swipe 共用用户-目标并发锁。
- 已经划过的目标按幂等请求处理，不重复扣额度或金币。
- 同一用户和目标使用稳定 operation key。
- Redis 原子预留 cards、right swipe 和赠送额度/金币价格。
- 金币扣减必须使用 operation key 保证 payment 侧幂等。
- Match 本地事务完成后操作状态才变为 COMPLETED。
- 金币不足时归还已预留配额。

#### 用户交互流程

```text
点击 Super Hi
  → 检查历史与未完成操作
  → 首次操作预留配额
  → 保存可恢复操作
  → 必要时幂等扣金币
  → 本地事务保存 SUPER_HI 划卡和 Match
  → 清理 Like、写 Outbox
  → 标记操作完成
  → 返回 Match
```

#### 故障恢复

- 已预留配额但扣费超时：保留操作，不贸然回滚。
- 金币明确不足：归还配额并删除未完成操作。
- 金币成功、本地事务失败：后台每 30 秒继续完成。
- 已完成操作重试：直接返回保存的 Match。

#### 当前边界

Redis 已预留、数据库操作记录尚未写入时若进程崩溃，可能留下孤儿 Redis marker；当前没有自动对账清理。

## 六、关系和配额查询

### F004 查看匹配列表

#### 功能描述

用户查看自己最近建立的匹配关系和对方基本资料。

#### 业务规则

- 最多返回 50 条。
- Match 表使用标准化 low/high 用户对，避免 A-B 与 B-A 重复。
- 某个用户资料缺失时仍保留 Match，只是展示信息不完整。
- 当前只支持第一页，预留的 page token 尚未参与查询。

#### 用户交互和数据流

```text
打开匹配列表
  → 查询本人位于 low/high 任一侧的 Match
  → 计算每条关系的另一方 ID
  → 批量获取另一方资料
  → 按匹配时间倒序展示
```

### F005 查看今日配额

#### 功能描述

用户查看当前订阅档位对应的每日上限、已使用量和 Super Hi 金币价格。

#### 业务规则

- 配额按 UTC 日期分桶。
- cards、right swipe、Super Hi 存在同一个 Redis HASH。
- 查询只读取，不初始化、不扣减。
- Redis 字段缺失或格式错误按 0。
- payment 查询失败时客户端按 FREE 档位降级。
- Redis 不可用时没有数据库兜底。

### F006 查看谁喜欢了我

#### 功能描述

用户查看发给自己的有效单向 Like。已经升级为 Match 的双方 Like 会被软删除。

#### 业务规则

- 单页最多 50 条。
- 按喜欢时间倒序。
- 资料批量从 user-service 获取。
- 当前 next token 只是末条时间戳，后续请求没有使用。
- `totalUnread` 等于当前页条数，不是真实未读总数。

### F007 查看谁访问了我

#### 功能描述

用户查看访问过自己主页的人、最近访问时间和累计访问次数。

#### 业务规则

- 相同 visitor-viewer 关系聚合为一条记录。
- 多次访问更新最近时间并增加次数。
- 单页最多 50 条。
- 当前分页和未读统计与 Like 列表一样未完整实现。
- 高并发下“先查再更新”可能丢失部分访问增量。

### F008 上报主页访问

#### 功能描述

用户访问他人主页时异步记录 Visit。

#### 业务规则

- 自己访问自己直接忽略并返回成功。
- 非自访问提交到当前实例的异步线程池。
- 返回成功只表示任务已入本机队列，不表示数据库已经写入。
- 数据库写入失败只记录日志。

#### 当前边界

服务重启会丢失尚未执行的内存任务。这条链路还不是持久化可靠异步，不能与 Match Outbox 的可靠性混为一谈。

## 七、后台支持流程

| 流程 | 作用 | 当前状态 |
| --- | --- | --- |
| D1 日更推荐 | 根据最近右划偏好重建个人 Feed | 已实现；活跃用户分页和原子替换有缺陷 |
| Match Outbox | 匹配后调用 IM | Match 侧可靠；IM 调用和 event key 去重未闭环 |
| DH 延迟匹配 | 15 秒～2 分钟后创建 DH Match | 已持久化、带租约和重试 |
| Super Hi 恢复 | 恢复扣费与本地事务间的中间状态 | 已实现 |
| ONLINE/OFFLINE 计划 | 为真人生成分散的 DH Like/Visit | 已实现计划生成 |
| DH 互动执行 | 到期写 Like/Visit | 持久化任务，但单条写与删任务事务未生效 |

## 八、全局业务边界

| 边界 | 当前情况 |
| --- | --- |
| IM 副作用 | im-service 尚未实现三个目标操作 |
| Outbox 端到端幂等 | event key 未传给 IM 去重 |
| MQ | 当前没有接入 |
| D1 活跃用户 | 超过 500 时重复处理第一批 |
| D1 队列替换 | `DEL + RPUSH` 中间可见空队列 |
| Feed 空队列重建 | 同步且无单用户锁 |
| Like/Visit 分页 | 只有第一页 |
| Visit 上报 | 本机异步，重启可丢 |
| DH Executor | 同类调用导致事务注解失效 |
