# Match Service 面试考点

## 1. 如何介绍 Match Service

### 1.1 这个服务负责什么

**推荐回答**

Match Service 是交友业务中的关系撮合服务，核心职责可以分成四组：

1. 为用户生成并维护每日推荐候选池，提供 Feed 浏览能力。
2. 接收左滑、右滑和 Super Hi 等互动，维护喜欢关系、配额和匹配关系。
3. 在互相喜欢或模拟用户延迟匹配时创建 Match，并通过 Outbox 可靠驱动会话和系统消息。
4. 为模拟用户生成在线、离线、喜欢和访问等行为，使互动节奏接近真实用户。

它不是单纯的“左右滑接口”，而是一个同时涉及推荐池、并发计数、关系状态机、延迟任务、分布式事务和最终一致性的服务。

### 1.2 服务中最值得讲的技术点

- Redis LIST 消费式 Feed 与 D0/D1 两级候选池。
- Redis Lua 原子扣减每日配额。
- 用户对锁、历史幂等与数据库事务共同保证 Swipe 正确性。
- PostgreSQL 延迟任务替代内存定时器，支持重启恢复和多实例抢占。
- Transactional Outbox 保证“匹配落库”和“通知 IM”最终一致。
- Super Hi 通过业务状态表、支付幂等键和恢复任务实现 Saga 补偿。
- 后台模拟互动计划通过持久化任务、租约、重试和去重约束执行。

## 2. Feed 与推荐池

### 2.1 为什么 Feed 使用 Redis LIST

**问题**

为什么不用数据库分页，而是把候选人放进 Redis LIST，再通过 `LPOP` 消费？

**推荐回答**

Feed 是一次性浏览场景。Redis LIST 能同时表达“有序候选队列”和“已消费即移除”：

1. 生成阶段按推荐顺序 `RPUSH`。
2. 请求阶段用 `LPOP` 依次领取。
3. 已经弹出的候选不会在当前列表中重复出现。
4. Redis 操作延迟低，适合高频翻卡。

但 `LPOP` 只保证单条领取原子性，并不保证“取出、过滤、返回”整体原子。如果候选随后被过滤，卡片不会自动放回；服务通过多轮补取降低返回不足，但仍需要接受候选被消耗的语义。

**追问**

如果必须保证一次请求完整领取 N 张卡且失败可回滚，可以使用 Lua 批量弹出、处理中队列、租约或 Redis Stream，但复杂度会明显上升。

### 2.2 D0 和 D1 分层解决了什么问题

**推荐回答**

- D1 是次日基础池，由定时任务提前批量生成，减少在线请求计算量。
- D0 是当日实时池。当缓存缺失或不足时，根据当前用户状态同步生成。
- 请求优先消费 D0；D0 不足时可以利用 D1 或重新生成补足。

这种设计把大量可预计算工作移到离线任务，同时保留在线兜底，兼顾响应速度和可用性。

**关键风险**

当前 D1 生成器虽然维护了 `offset`，查询却固定 `LIMIT 500`，没有把 offset 应用到 SQL，数据量超过 500 时可能反复处理第一批用户。此外，`DEL` 后再 `RPUSH` 不是原子替换，中间窗口会看到空池。

### 2.3 Feed 如何避免重复和无效候选

**推荐回答**

生成阶段会排除自己、已滑过用户、已有匹配、被拉黑或不符合基础条件的用户；领取阶段还会再次检查已滑集合，防止缓存陈旧导致重复曝光。领取逻辑最多执行固定轮次，避免脏数据或大量过滤项导致无限循环。

**当前实现细节**

代码注释提到批量检查，但实际逐个执行 `SISMEMBER`。当候选量增大时会产生多次 Redis 往返，可以改成 pipeline、`SMISMEMBER` 或在 Lua 中完成批量领取与过滤。

### 2.4 如何处理缓存击穿

**推荐回答**

当用户的 D0 Feed 不存在时，多个并发请求可能同时重建。可使用单飞锁或分布式锁：

1. 先检查缓存。
2. 未命中时尝试获取用户维度的重建锁。
3. 获锁者生成 Feed。
4. 未获锁者短暂等待后再次读取。
5. 生成结果设置合理 TTL。

当前实现具备同步重建兜底，但面试中应主动说明高并发下还可补充单飞控制。

## 3. 高并发配额设计

### 3.1 为什么配额扣减使用 Lua

**问题**

为什么不能先 `GET` 再 `DECR`？

**推荐回答**

`GET` 和 `DECR` 是两个独立操作，并发请求都可能读到“还有余额”，最终造成超扣。Lua 脚本在 Redis 单线程执行模型中原子完成：

1. 判断配额键是否存在。
2. 不存在时初始化每日额度和过期时间。
3. 判断剩余额度是否足够。
4. 足够则扣减并返回新余额。
5. 不足则拒绝且不改变余额。

这样避免了检查与扣减之间的竞态。

### 3.2 为什么数据库失败后要补回 Redis 配额

**推荐回答**

Swipe 先在 Redis 扣额度，再执行数据库事务。如果数据库事务失败但配额不补偿，用户没有完成业务动作却损失次数。因此调用链使用 try/catch，在业务事务异常时执行 Redis 回补。

这里属于跨存储补偿，不是强事务。补偿也可能失败，因此生产设计还应加入补偿日志、重试任务或以数据库账本为最终依据进行对账。

### 3.3 每日配额的过期时间应如何设置

**推荐回答**

键应该在业务时区的下一自然日边界过期，而不是简单固定 24 小时。固定 24 小时会让每个用户的重置时刻随首次使用时间漂移。还要考虑：

- 服务统一使用哪个时区。
- 夏令时地区是否影响边界。
- Redis 键丢失时如何重新初始化。
- 配额调整后旧键如何迁移。

## 4. Swipe 的事务、锁与幂等

### 4.1 Swipe 完整链路如何保证正确

**推荐回答**

一次 Swipe 的关键顺序是：

1. 规范化两个用户 ID，获取用户对维度的分布式锁。
2. 查询历史滑动记录，命中则按既有结果幂等返回。
3. 原子扣减对应类型的每日配额。
4. 调用独立 Spring Bean 上的事务方法写入滑动和喜欢关系。
5. 如果是真实用户右滑，检查对方是否已经喜欢自己；满足条件则创建匹配。
6. 如果是模拟用户右滑，则创建持久化延迟匹配任务，不立即匹配。
7. 数据库失败时回补配额。
8. 成功后更新已滑缓存并释放锁。

锁防止同一用户对并发修改；唯一约束和历史记录提供持久幂等；数据库事务保证核心关系写入的一致性。

### 4.2 为什么事务逻辑要放到独立 Bean

**推荐回答**

Spring 的 `@Transactional` 通常通过代理生效。同一个对象内部用 `this.method()` 调用事务方法会绕过代理，事务可能不生效。将数据库核心逻辑放到 `MatchTransactionService`，由 `SwipeService` 注入并调用，能确保经过 Spring 代理。

这是面试中常见的“事务自调用失效”问题。

### 4.3 分布式锁为什么使用用户对，而不是只锁当前用户

**推荐回答**

匹配状态属于两个用户之间的关系。A 右滑 B 和 B 右滑 A 可能同时发生。如果分别锁 A 和 B，两个请求仍可并发创建相同匹配。把两个 ID 排序后生成稳定的 pair key，无论请求方向如何都竞争同一把锁。

数据库还需要标准化 pair 唯一约束作为最终防线，因为锁可能因网络分区、租约问题或误配置失效。

### 4.4 看门狗锁解决什么问题

**推荐回答**

如果给锁设置固定短 TTL，业务执行时间超过 TTL 后锁会提前释放，另一个请求进入临界区。Redisson 看门狗会在持锁线程仍存活时续租，降低长事务导致锁失效的风险。

但锁不能替代数据库唯一约束和幂等记录，因为进程暂停、Redis 故障或客户端失联仍可能破坏锁语义。

### 4.5 当前 Swipe 还有什么边界风险

- 数据库成功后执行 `markSwiped`，该缓存写没有独立容错；若失败，请求可能报错，但重试会因历史幂等直接返回，未必重新修复缓存。
- Redis 配额补偿本身不是可靠消息，补偿失败需要对账机制。
- 分布式锁扩大了串行范围，要监控锁等待时间和热点用户对。

## 5. 匹配创建与 Outbox

### 5.1 为什么匹配成功后不能直接同步调用 IM

**推荐回答**

数据库事务和远程 IM 调用无法组成普通本地事务：

- 先写数据库再调 IM：数据库提交后 IM 失败，会有匹配但没有会话。
- 先调 IM 再写数据库：IM 成功后数据库回滚，会有孤立会话。

因此事务内同时写 Match 和 Outbox 事件。事务提交后，由后台任务发送 Outbox。这样能保证只要匹配存在，通知事件就不会因进程崩溃而永久丢失。

### 5.2 Transactional Outbox 的完整状态如何流转

**推荐回答**

1. 创建匹配的同一数据库事务中插入待发送 Outbox。
2. 调度器批量 claim 到期事件。
3. SQL 使用 `FOR UPDATE SKIP LOCKED`，多实例不会领取同一行。
4. claim 时写入 workerId 和租约到期时间。
5. worker 调用 IM 创建会话并发送系统消息。
6. 全部成功后标记成功。
7. 失败则记录错误、增加重试次数并计算下次执行时间。
8. 超过最大次数进入 DEAD，交给告警和人工补偿。
9. worker 崩溃时，租约到期后其他实例可重新领取。

### 5.3 `SKIP LOCKED` 有什么价值

**推荐回答**

多个 worker 扫描同一任务表时：

- `FOR UPDATE` 锁住领取到的行。
- `SKIP LOCKED` 让其他 worker 跳过已锁行，继续领取别的任务。

它既避免重复领取，又减少相互等待，适合数据库任务队列。但要配合小批量、合适索引、租约和失败重试。

### 5.4 Outbox 是否天然保证“恰好一次”

**推荐回答**

不能。Outbox通常提供至少一次投递：

1. 下游调用成功。
2. worker 在标记 Outbox 成功前崩溃。
3. 租约到期后事件再次执行。

因此下游必须支持幂等。当前服务生成稳定 `eventKey`，但 IM 接口还需要真正接收并落库去重键；否则重复重试仍可能创建重复会话或消息。面试时应明确“稳定键只有传递到并被下游消费才有效”。

### 5.5 为什么当前代码仍不能算链路完全闭环

代码侧的 IM 客户端还有三个调用没有真正实现完整下游语义，而且事件幂等键尚未贯穿到 IM 的去重存储。因此当前 Outbox 的持久化、抢占和重试机制已经存在，但端到端幂等仍需要下游配合。

## 6. 延迟匹配任务

### 6.1 为什么模拟用户右滑要延迟匹配

**推荐回答**

模拟用户如果右滑后立即匹配，会表现得机械且容易暴露自动化。服务根据设定延迟创建任务，到期后再检查关系并创建匹配，使交互时间更接近真实行为。

### 6.2 为什么不能使用进程内 `ScheduledExecutorService`

**推荐回答**

内存任务存在明显可靠性问题：

- 服务重启后任务丢失。
- 多实例无法自然协调。
- 无法查询任务状态。
- 失败重试和死信处理困难。

当前使用 PostgreSQL 持久化延迟任务，保存执行时间、状态、重试次数、worker 和租约。调度器每 5 秒领取一批到期任务，支持多实例、重启恢复和失败重试。

### 6.3 延迟任务如何处理重复执行

**推荐回答**

任务领取只能减少并发重复，不能排除 worker 在业务成功后、更新任务状态前崩溃。因此执行方法仍需幂等：

- 创建匹配使用标准化 pair 唯一约束。
- 执行前检查已有匹配或关系状态。
- 重复插入转换为查询既有结果或安全忽略。
- 任务有最大重试次数，超过后进入失败状态。

## 7. Super Hi 的 Saga 与恢复

### 7.1 Super Hi 为什么比普通右滑复杂

Super Hi 同时修改三个不同边界：

1. Redis 中的每日使用标记或配额。
2. 支付服务中的金币余额。
3. Match Service 数据库中的业务记录。

它们不能放入同一个本地事务，因此需要显式状态机、幂等键和恢复任务。

### 7.2 Super Hi 的状态机如何工作

**推荐回答**

1. Redis 原子占用当日 Super Hi 名额。
2. 数据库创建 `QUOTA_RESERVED` 操作记录。
3. 使用稳定业务幂等键调用支付扣金币。
4. 扣款确认后将状态推进为 `COINS_CHARGED`。
5. 执行 Super Hi 的喜欢或匹配业务。
6. 完成后标记 `COMPLETED`。
7. 定时恢复任务扫描中间状态，按状态继续执行而不是从头盲目重做。

状态表让系统知道失败发生在哪一步，支付幂等键避免恢复时重复扣款。

### 7.3 Redis 占额后进程立刻崩溃怎么办

**推荐回答**

如果 Redis 已占额、数据库操作记录尚未创建，恢复任务看不到这次操作，形成孤儿标记窗口。改进方式包括：

- 先创建数据库意图记录，再使用带 operationId 的 Redis Lua 占额。
- Redis 保存 operationId，而不只是布尔标记。
- 增加扫描 Redis 与数据库不一致的对账任务。
- 让占额键使用较短租约，成功后再转换为当日完成标记。

### 7.4 Saga 和分布式事务的区别

Saga 不追求跨服务瞬时强一致，而是把业务拆成多个本地事务，并为失败设计重试或补偿。它适合支付、库存、互动等长链路，但必须明确：

- 每一步的幂等键。
- 状态推进条件。
- 可重试与不可重试错误。
- 补偿动作。
- 人工介入和对账方式。

## 8. 查询、分页与未读数

### 8.1 游标分页为什么优于 offset 分页

**推荐回答**

互动列表通常按时间倒序。使用 offset 时，分页期间插入新记录会导致重复或漏读；大 offset 的数据库扫描成本也高。游标分页使用 `(created_at, id)` 作为稳定排序边界：

```sql
WHERE (created_at, id) < (:cursorTime, :cursorId)
ORDER BY created_at DESC, id DESC
LIMIT :pageSize
```

这样性能和稳定性更好。

### 8.2 当前分页实现有哪些问题

- `ListMatches` 接收了 token，但查询没有消费 token，实际始终从第一页开始。
- Like/Visit 列表会生成下一页 token，但后续请求没有解析并应用该 token。
- `totalUnread` 当前按本页结果数量计算，不代表全部未读总数。

这类问题的危险在于接口表面具备分页字段，但实现没有形成闭环。评审时不能只看 DTO，要追踪 token 的生成、解析和 SQL 条件。

### 8.3 未读数应该如何设计

可以选择：

- 数据库精确统计：简单但高频查询成本高。
- Redis 计数：读取快，但需要处理消息重复、回滚和对账。
- 已读游标：保存最后已读时间或 ID，通过查询计算增量。
- 异步聚合：事件驱动更新计数，允许短暂最终一致。

选择取决于数据量、实时性要求和是否允许近似值。

## 9. 访问记录与异步执行

### 9.1 `@Async` 记录访问有什么优缺点

**推荐回答**

优点是主请求不用等待访问记录写库，降低接口延迟。缺点是任务只存在本进程内：

- 应用退出时未执行任务可能丢失。
- 队列满时可能被拒绝。
- 调用方无法感知最终失败。
- 不适合必须可靠保存的业务事件。

如果访问记录只是弱一致埋点，`@Async` 可以接受；如果用于计费、权益或重要通知，应改为持久化消息、Outbox 或数据库任务。

### 9.2 如何避免重复访问记录

先明确产品语义：

- 只关心“是否访问过”：使用 `(visitor, target)` 唯一键并更新最后访问时间。
- 关心每天一次：使用 `(visitor, target, date)` 唯一键。
- 关心每次访问：保留明细事件，并通过 eventId 幂等。

数据库唯一约束应作为最终防重，而不是只依赖 Redis。

## 10. 模拟用户互动计划

### 10.1 为什么要区分 BH 和 DH

**推荐回答**

BH 可理解为参与即时互动决策的模拟账号，DH 则通过离线计划和延迟任务表现出更自然的行为节奏。两类账号在推荐池占比、右滑后的匹配时机、在线状态和互动计划上不同，因此不能只用一个布尔字段处理所有逻辑。

### 10.2 在线与离线计划如何生成

服务按用户状态和计划规则生成时间窗口：

1. 在线计划决定某段时间是否表现为在线。
2. 离线计划为未来时间段生成访问或喜欢任务。
3. 任务持久化到数据库。
4. 执行器按到期时间和租约领取。
5. 成功后完成或删除任务；失败则重试。

这种方式把“行为计划”和“实际执行”解耦，便于扩容、恢复和观察。

### 10.3 当前实现中最值得指出的两个问题

1. 计划生成依赖 IM 在线用户列表；如果远程调用失败并返回空列表，游标仍可能推进，从而跳过本轮应处理用户。
2. 执行器中事务方法存在同类内部调用，`@Transactional` 可能因代理自调用而失效；业务写入与任务硬删除也可能无法原子提交。

改进方式是只在成功获取依赖数据并完成生成后推进游标，并把事务边界移动到独立 Bean，或使用 `TransactionTemplate`。

## 11. 数据库任务队列设计

### 11.1 一个可靠任务表至少需要哪些字段

- 业务唯一键或幂等键。
- payload 或关联业务 ID。
- `status`。
- `execute_at` / `next_retry_at`。
- `retry_count` / `max_attempts`。
- `worker_id`。
- `lease_until`。
- `last_error`。
- 创建时间和更新时间。

索引通常覆盖 `(status, execute_at)` 或 `(status, next_retry_at)`，以支持高效扫描到期任务。

### 11.2 租约时间如何设置

租约必须大于绝大多数任务执行时间，否则正常任务会被重复领取；也不能过长，否则 worker 崩溃后的恢复太慢。应基于执行耗时分位数设置，并考虑：

- 长任务是否续租。
- 下游超时时间。
- 单批任务数量。
- 数据库事务持锁时间。
- 任务幂等能力。

当前延迟匹配使用 2 分钟租约、最多 10 次尝试，调度周期 5 秒、单批 100 条。面试中可以说明这些是配置与容量评估的起点，不是普适常量。

## 12. 故障场景推演

### 12.1 数据库提交后服务崩溃

- Swipe 核心数据已持久化，可通过历史记录幂等返回。
- 匹配对应 Outbox 与 Match 在同一事务中，重启后 worker 会继续投递。
- 数据库成功后的 Redis 已滑缓存可能尚未更新，需要查询兜底或缓存修复。

### 12.2 IM 调用成功后 worker 崩溃

Outbox 没有标记成功，租约到期后会重试。必须依赖 IM 端使用 eventKey 幂等，否则可能重复创建会话或消息。

### 12.3 Redis 不可用

- Feed 无法正常领取或重建缓存。
- 配额无法原子扣减。
- Super Hi 无法占用当日名额。

应根据产品容忍度选择失败关闭或降级。涉及付费和权益的操作通常应失败关闭，不能在无法校验时放行。

### 12.4 worker 执行到一半宕机

任务租约到期后重新领取；业务动作必须可幂等。不能把“任务表只执行一次”当成前提。

## 13. 代码评审高频问题

### 13.1 看到 `@Transactional` 应检查什么

1. 方法是否是 public。
2. 是否从 Spring 代理外部调用。
3. 是否存在同类内部调用。
4. 异常是否被吞掉。
5. 抛出的异常类型是否触发回滚。
6. 事务中是否包含慢远程调用。
7. 多张表写入是否真的在同一数据源和事务管理器中。

### 13.2 看到“幂等”应检查什么

1. 幂等键由什么组成，是否稳定。
2. 去重状态存在哪里。
3. 检查与写入是否原子。
4. 并发请求能否同时通过检查。
5. 下游是否也消费幂等键。
6. 幂等记录保留多久。
7. 相同请求重试时是否返回一致业务结果。

### 13.3 看到定时任务应检查什么

1. 多实例是否重复执行。
2. 任务是否持久化。
3. 服务重启能否恢复。
4. 是否有租约、续租和超时回收。
5. 是否有限次重试和死信。
6. 执行逻辑是否幂等。
7. 是否有监控、积压指标和人工重放。

### 13.4 看到分页 token 应检查什么

不能只看“是否返回 token”，还要检查：

1. token 是否包含稳定排序键。
2. 是否签名或校验，防止篡改。
3. 下一次请求是否解析 token。
4. SQL 是否真正应用边界条件。
5. 排序字段相同时是否使用唯一 ID 打破平局。

## 14. 生产改进优先级

### P0：正确性与资金安全

1. 完成 IM 三个下游调用，并让稳定 eventKey 贯穿到下游去重。
2. 修复 Match、Like、Visit 列表 token 未消费的问题。
3. 修复 D1 分批查询 offset 未生效。
4. 修复 DH 执行器事务自调用和“业务写入 + 删除任务”非原子问题。
5. 为 Super Hi Redis 孤儿占额增加 operationId 或对账恢复。

### P1：可靠性与可观测性

1. 为 Redis 配额补偿建立持久化重试或对账。
2. RecordVisit 从本地 `@Async` 升级为持久化事件。
3. 对 Outbox、延迟任务和互动任务增加积压量、最老任务年龄、失败率和 DEAD 告警。
4. 远程依赖失败时不要错误推进计划游标。
5. Feed 重建增加用户维度单飞控制。

### P2：性能与体验

1. 已滑检查改为 pipeline、`SMISMEMBER` 或 Lua 批处理。
2. D1 池使用临时键加原子 rename，消除 `DEL + RPUSH` 空窗。
3. 优化未读总数模型，避免用当前页大小冒充总数。
4. 根据线上耗时调整批量大小、租约和并发度。

## 15. 推荐的面试回答结构

讲任何一个 Match Service 方案时，可以按下面顺序回答：

1. **业务目标**：这个功能解决什么用户问题。
2. **正常流程**：请求从入口到数据库、Redis和下游如何流转。
3. **并发控制**：锁、Lua、唯一约束或事务分别保护什么。
4. **幂等设计**：重复请求、重复投递和重复执行如何处理。
5. **故障恢复**：进程崩溃、网络超时、下游失败后怎么恢复。
6. **一致性选择**：哪些必须强一致，哪些允许最终一致。
7. **当前边界**：代码现在还存在哪些风险。
8. **演进方案**：如何根据流量和业务价值逐步加强。

不要只罗列 Redis、分布式锁、Outbox 等名词。高质量回答需要把组件放进一条完整业务链路，并说明它解决的具体故障场景。
