# User Service 业务清单

> 本文从产品和业务视角说明“用户能做什么、系统遵循什么规则”。不展开远程调用字段、返回结构、错误码和代码调用链；实现细节见《user-service-业务流程详解》。

## 一、模块定位与边界

user-service 是用户身份映射和用户资料的领域服务，负责回答三类问题：

1. 一个已经过上游验证的外部身份对应哪个内部用户；
2. 用户的基础资料、兴趣和监管状态是什么；
3. 其他服务批量展示用户时，应取得哪些稳定资料。

它当前持有五类数据：用户主资料、手机号绑定、第三方账号绑定、设备绑定、兴趣标签。

### 1.1 服务负责

- 把手机号、第三方账号或设备标识解析为内部 userId；
- 首次进入时创建待 onboarding 的 placeholder 用户；
- 保存和读取昵称、年龄、性别、生日、地区、简介、职业、教育、身高等资料；
- 保存用户兴趣标签及其展示顺序；
- 判断数据库监管状态和运营封禁集合；
- 为头像上传生成对象路径并校验确认请求；
- 为 post、match、im、gateway 等服务提供用户资料。

### 1.2 服务不负责

- 不校验短信验证码或第三方 token；
- 不签发、刷新或验证 JWT；
- 不管理密码；
- 不管理好友、关注、拉黑和匹配关系；
- 不处理聊天连接或 IM token；
- 不负责支付、订阅和钱包；
- 不接收头像二进制文件；
- 当前不生产或消费 MQ 消息，也没有定时任务。

## 二、用户角色

| 角色 | 业务含义 | 主要能力 |
|---|---|---|
| 未完成资料的新用户 | 已获得 userId，但 `pending=1` | 完成 onboarding、读取当前资料 |
| 普通真人用户（BH） | 默认创建的用户类型 | 编辑资料、管理兴趣、头像上传 |
| 数字人用户（DH） | 数据模型已预留 `user_type=2` | 当前缺少本服务的创建和完整查询链路 |
| 其他业务服务 | 需要展示或判断用户属性 | 单人/批量资料读取、封禁检查 |
| 运营或风控系统 | 维护监管状态 | 当前只有读取约定，仓库内没有完整写入入口 |

## 四、身份进入

### F001 手机号身份解析

#### 功能说明

上游完成短信验证后，把手机号交给本服务。系统先规范化为国际 E.164 格式，再在当前 App 维度查找绑定。

#### 业务规则

- 手机号必须能被识别为有效国际号码；
- 同一手机号在同一 App 内只能绑定一个用户；
- 同一手机号在不同 App 可分别拥有用户；
- 已绑定时返回原用户，并尝试刷新最近打开时间；
- 未绑定时创建默认真人 placeholder；
- 新用户昵称为 `User_{userId}`，资料状态为待完成；
- 当前手机号绑定是物理唯一，软删除后也不能直接重绑。

#### 用户交互

1. 用户在 gateway 完成短信验证；
2. 系统查找或创建用户；
3. 若资料待完成，客户端进入 onboarding；
4. 若资料已完成，客户端继续登录后的业务流程。

#### 实现状态

user-service 内部能力已实现，但仓库当前 mobile-gateway 客户端没有调用这条身份解析链路，也没有紧接着执行本服务的封禁判断，因此完整登录闭环尚未在当前代码中形成。

### F002 第三方身份解析

#### 功能说明

上游验证第三方授权后，使用平台标识、第三方用户 ID 和 App 维度查找用户。

#### 业务规则

- 支持的契约平台为 Google、Facebook、Apple；
- 未指定平台会被拒绝；
- 同一平台账号在同一 App 内只有一个活动绑定；
- 活动绑定软删除后允许重新绑定；
- Google 邮箱可随首次绑定记录，但不是登录凭证；
- 已绑定和新建 placeholder 的后续分流与手机号一致。

#### 实现状态

服务内已实现，当前 gateway 尚未接入。服务只信任上游传来的第三方用户 ID，不自行验证 OAuth token。

### F003 设备快速进入

#### 功能说明

用户没有短信或第三方授权时，可用设备标识快速获得账号。

#### 业务规则

- 设备标识、设备平台和 App 共同确定唯一活动绑定；
- 设备平台必须明确；
- 活动绑定软删除后允许重新绑定；
- 新建账号默认是待 onboarding 的真人用户；
- 当前没有把设备账号升级为手机号/三方账号的绑定能力；
- 当前没有 DeviceCheck、App Attest、Play Integrity、IP 频控等反作弊校验。

#### 风险和例外

设备标识可能因卸载、重装或系统重置而变化，旧账号可能无法找回；攻击者也可能批量伪造设备标识。当前功能更适合 MVP 快速体验，不应被描述为高可信身份认证。

## 五、监管状态

### F004 封禁状态判断

#### 功能说明

系统综合短缓存、运营封禁集合和用户主表监管状态，判断用户是否受限。

#### 业务规则

- 正式封禁和暂停状态来自用户主表；
- 运营临时封禁来自 Redis 集合；
- 判定结果缓存 5 分钟，包括“正常”结果；
- 运营集合没有本服务内的写入入口；
- 不存在的 userId 当前会被当作正常；
- 具体封禁时间当前无法提供。

#### 一致性预期

当前不是实时强一致。已经缓存为正常的用户，即使随后被加入运营集合，也可能在短缓存到期前继续被判定为正常。返回的“是否封禁”较可靠，但具体原因当前存在转换缺陷，调用方应避免只依赖原因字段。

## 六、资料读取和编辑

### F005 查看单个用户资料

#### 功能说明

按 userId 查看基础资料与兴趣，用于个人主页、帖子作者、匹配卡片等展示。

#### 业务规则

- 已逻辑删除或不存在的用户不可读取；
- 资料读取不要求调用者就是本人，也没有隐私字段可见性判断；
- 兴趣按用户设置顺序返回；
- 主资料和兴趣使用不同缓存，可能来自略有时间差的状态；
- 当前头像没有持久化列，因此始终为空；
- 最近打开时间的毫秒字段当前不会被正确填充。

#### 数据流

系统优先读取缓存；主资料或兴趣缺失时分别回源数据库，再组合成一份展示资料。

### F006 批量查看用户资料

#### 功能说明

一次补齐一组用户的资料，供列表型页面和其他服务使用。

#### 业务规则

- 一次最多接收 200 个 userId；
- 重复 userId 会去重；
- 返回顺序遵循去重后的首次出现顺序；
- 不存在的用户会被静默跳过，不返回空占位；
- 调用方可以选择是否附带兴趣；
- 当前批量结果同样没有头像。

#### 一致性预期

命中缓存的用户与回源数据库的用户可能来自不同时间点，批量结果不是数据库快照。对展示类场景通常可接受，不适合作为需要原子一致视图的结算或权限依据。

### F007 编辑基础资料

#### 功能说明

已登录用户修改昵称、年龄、地区、简介、职业、教育和身高。

#### 业务规则

- 修改身份以调用链传入的当前用户为准；
- 请求中若同时带目标 userId，不能修改其他用户；
- 未提供的字段保持不变；
- 昵称最长 64，年龄范围 0～150，地区/职业/教育最长 128，简介最长 500，身高范围 0～300；
- 空字符串会被当成“未提供”，因此不能用当前入口清空文字字段；
- 数值 0 在入口被当成“未提供”，因此不能显式把年龄或身高改成 0；
- 性别、生日、邮箱、联系电话、监管状态和用户类型不可由此功能修改。

#### 实现状态

服务内已实现。当前 mobile-gateway 的兼容版资料编辑只传昵称和简介，而且没有附带本服务要求的调用者身份 metadata，因此按现有代码该写链路不能正常完成。

### F008 完成 onboarding

#### 功能说明

新用户补充昵称、性别、生日及可选资料，把 placeholder 状态变为完成。

#### 业务规则

- 昵称、明确性别和生日必填；
- 完成后 `pending` 变为 0；
- 可同时提交初始兴趣；
- 主资料和兴趣数据库写入在同一事务内；
- 空兴趣列表不会清空旧兴趣，而是保留；
- 代码没有检查当前是否仍为 pending，所以该功能实际可以重复调用；
- 重复调用可以覆盖性别和生日，和“只允许首次写入”的产品意图不一致；
- 当前不校验生日是否未来日期，也未由生日派生年龄。

## 七、兴趣和头像

### F009 全量替换兴趣

#### 功能说明

用户提交当前完整兴趣集合，系统以本次提交覆盖旧集合。

#### 业务规则

- 空集合表示清空全部兴趣；
- 图片型兴趣最多 9 个；
- 独立入口限制总标签最多 50 个；
- 同一大类和标签组合不可重复；
- 按提交顺序保存并展示；
- 删除旧数据和写入新数据在同一事务内完成；
- 两个设备并发提交时，最终以最后提交成功的事务为准。

### F010 两阶段头像上传

#### 功能说明

客户端先取得上传地址和对象 key，再把图片直传对象存储，最后确认头像。

#### 业务规则

- 允许 jpg、jpeg、png、webp；
- 声明文件大小不得超过 10MB；
- 对象 key 只能位于当前用户的头像目录；
- 上传凭证设计有效期为 5 分钟；
- 用户只能确认自己目录下的对象。

#### 实现状态

当前仅完成参数校验和 key 生成。返回地址是占位字符串，确认时不检查对象是否存在，也不写入用户资料；因此用户完成操作后，资料中的头像仍为空。

## 八、兼容能力和跨服务依赖

### F011 兼容版资料能力

为旧 gateway 和 post-service 保留了简化版的单人读取、批量读取和资料编辑：

- 简化读取只展示 userId、昵称、原图 key、简介、年龄、性别和创建时间；
- 因头像尚未落库，原图 key 为空；
- 批量读取不附带兴趣；
- 兼容编辑仍受“只能修改自己”和调用者身份约束。

这组能力是迁移期兼容层，不应继续扩展新字段；新需求应使用完整资料模型。

### F012～F014 用户类型和候选召回

数据表和契约已经预留真人/数字人类型、年龄、性别、位置、颜值和种族等字段，但服务端没有实现用户类型查询、数字人候选召回和附近真人召回。

当前调用方的可见结果是：

- match-service 获取不到类型时使用未知值；
- match-service 获取不到候选时得到空集合；
- im-service 获取不到类型时按真人处理。

这些是降级结果，不代表“没有数字人”或“附近没人”。产品数据分析和排障时必须区分“真实空结果”与“能力未实现”。

## 九、后台支持流程

| 支持流程 | 作用 | 当前状态 |
|---|---|---|
| Flyway 启动迁移 | 创建五张用户域表、索引、约束和更新时间触发器 | 已配置 |
| Redis key 前缀初始化 | 启动时把配置写入静态 key 工厂 | 已实现 |
| gRPC 调用上下文注入 | 读取当前用户、设备和 trace 信息 | 已实现 |
| 资料/兴趣缓存过期 | 让旧数据最终回源 | 已实现，依赖 TTL |
| 封禁短缓存过期 | 让监管结果最终重新判定 | 已实现，TTL 5 分钟 |
| 运营封禁写入 | 维护运营集合并失效短缓存 | 本服务缺失 |
| 头像缩略图生成 | 生成 min/mid/original 三档 | 缺失 |
| MQ 生产/消费 | 异步传播用户变更 | 无 |
| 定时任务 | 清理、修复或刷新数据 | 无 |

## 十、全局业务边界

- `user_id` 是跨服务业务主键；数据库自增 `id` 不对外暴露。
- 数据库时间按 UTC 存储。
- 用户删除目前只有逻辑删除字段和级联约束设计，没有公开删除业务流程。
- 用户资料没有版本号，写冲突采用后提交覆盖。
- 缓存用于展示性能，不是权威数据源；数据库是主资料和兴趣事实源。
- 当前没有审计表、资料历史版本、删除恢复、账号合并和多身份补绑能力。
- 当前代码没有任何可证明的生产 QPS、延迟或容量数据，不能把理论优势表述成线上收益。
