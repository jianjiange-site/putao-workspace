# User Service 面试考点

> 回答原则：先讲业务和数据特征，再讲当前实现、事务与失败边界，最后把改进方案明确标成“演进方向”。不要把设计稿、Proto 预留或理论收益说成已上线事实。

## 一、如何介绍这个项目

### 1.1 30 秒版本

user-service 负责用户身份映射和用户资料。它把已由上游验证的手机号、第三方账号或设备标识解析为内部 userId，保存主资料和兴趣，并向 gateway、post、match、im 提供资料与监管判断。服务使用 PostgreSQL 作为事实源、Redis 做资料与封禁缓存、Redisson 控制同一凭证的并发注册，内部通过 gRPC 暴露能力。

### 1.2 90 秒版本

可以按四段回答：

1. **业务边界**：gateway 管短信/OAuth/JWT，会话凭证不落 user-service；user-service 只管理“这个人是谁”和“资料是什么”。
2. **核心模型**：一张 `user_info` 主表，三张外部身份绑定表，一张兴趣表；`user_id` 是跨服务 Snowflake 业务主键。
3. **关键设计**：身份解析使用细粒度分布式锁、唯一约束和冲突后重查；资料采用 Cache Aside；兴趣用事务内全量替换。
4. **诚实边界**：注册的 placeholder 与绑定当前不在同一事务；头像只是占位；用户类型和两类召回 RPC 尚未实现；缓存失效发生在事务提交前。

### 1.3 最值得讲的技术点

优先级建议：

1. 身份解析的并发、幂等与事务缺口；
2. 主资料/兴趣拆分缓存及事务提交前删缓存的风险；
3. PostgreSQL 部分 EXCLUDE 约束支持软删除后重绑；
4. 兴趣全量替换的事务与并发覆盖；
5. 封禁多来源判定和故障策略；
6. Proto 已声明但服务未实现时，下游如何降级及其隐患。

## 二、服务边界与协议

### Q1：user-service 和 mobile-gateway 如何分工？

**简答**

gateway 负责验证短信、第三方 token 和 JWT，并管理 access/refresh token；user-service 接收已经验证的外部身份，解析 userId 和持久化资料。这样会话安全逻辑与用户领域数据解耦。

**为什么符合数据特征**

会话凭证短生命周期、更新频繁且安全策略集中；用户资料长生命周期、需要跨业务复用。分开后，资料服务不需要持有 JWT 密钥或 OAuth SDK。

**失败边界**

当前仓库中的 gateway 客户端只接了兼容资料接口，没有串通三类身份解析和封禁检查；资料编辑也没有附带 `x-user-id` metadata。因此“边界设计合理”不等于“当前登录闭环已完成”。

**追问**

- 谁验证手机号和第三方 token？
- 为什么 user-service 仍要二次规范化手机号？
- 服务间如何传 caller userId？

### Q2：为什么内部使用 gRPC？

**简答**

项目需要多个 Java 服务共享稳定的强类型契约，Proto 能生成 stub 并在编译期暴露字段和接口变化。当前接口是普通 unary RPC，并未使用 streaming。

**项目事实**

- gRPC server 监听 19081；
- HTTP 18081 主要用于 Actuator；
- `UserGrpcService` 继承生成的基类并转发给两个 mixin；
- 调用者身份通过 metadata 进入 gRPC Context。

**不要夸大**

项目没有压测数据，不能说“比 REST 快 2～3 倍”；也不能把“gRPC 支持流式”说成当前项目已使用。

### Q3：gRPC Context 为什么比 ThreadLocal 更合适？

**简答**

Context 是 gRPC 的请求级传播机制，能沿拦截器和异步回调传递 metadata，不要求业务方法显式增加 userId/traceId 参数。当前拦截器把 `x-user-id`、`x-device-id`、`x-trace-id` 放进 Context。

**边界**

当前代码没有把生成的 traceId 写入 MDC，而日志 pattern 又读取 MDC，所以“Context 中有 traceId”不能直接推导为“日志一定带 traceId”。

### Q4：异常是怎样映射成 gRPC Status 的？

**简答**

项目同时存在全局 `GrpcExceptionAdvice` 和入口手动 catch。实际大多数路径由 `UserGrpcService.sendBizError` 处理：找不到用户映射 NOT_FOUND，封禁异常映射 PERMISSION_DENIED，其他 BizException 都映射 INVALID_ARGUMENT。

**关键辨析**

不能只读 Advice 就回答“普通业务异常都是 FAILED_PRECONDITION”。入口已经捕获的异常不会再走 Advice；甚至内部错误被重新包装后也可能成为 INVALID_ARGUMENT，这是当前需要收敛的实现问题。

**演进方向**

统一保留一套异常转换机制，并为权限、参数、前置条件、内部错误建立可测试的映射表。

## 三、身份解析、锁与幂等

### Q5：为什么三类 ResolveOrCreate 要加分布式锁？

**简答**

同一手机号、第三方账号或设备 ID 可能被多个请求同时解析。锁按“凭证 + App”串行化同一业务键，减少重复创建和唯一约束冲突；不同凭证仍可并行。

**当前实现**

```text
phone:  phoneE164 + appName
third: platform + thirdPartyUserId + appName
device: deviceId + platform + appName
wait=3s, lease=30s
```

拿锁后再次查绑定，未命中才创建 placeholder；插入仍以数据库唯一约束兜底，冲突后重查赢家。

**追问：有锁为何还要唯一约束？**

锁可能因 Redis 故障、租期到期、配置错误或其他写入路径而失效；数据库约束才是数据层最终防线。

### Q6：当前注册链路是否事务安全？

**简答**

不完全安全。`createPlaceholder()` 标了 `@Transactional`，但从同一个 Bean 内部调用，默认 Spring 代理不会生效；外层解析方法也没有事务。因此创建 `user_info` 和插入绑定通常是两个独立提交。

**失败后果**

- 绑定插入失败可能留下 pending placeholder；
- 并发输家重查后能返回赢家，但自己的 placeholder 可能残留；
- 这不影响绑定唯一性，却影响数据整洁和用户量统计。

**演进方向**

把“建用户 + 建绑定”放入独立 Bean 的公共事务方法；锁用于降低冲突，唯一约束继续兜底。再增加孤儿 placeholder 的可审计清理规则。

### Q7：这三条身份解析能称为幂等吗？

**简答**

从调用结果看，同一活动凭证重复请求通常返回同一 userId，属于业务结果近似幂等；从副作用看，因为事务缺口可能产生额外 placeholder，所以不能称为完全无副作用的严格幂等。

**回答结构**

1. 幂等键是外部凭证和 App；
2. 锁内二次查询避免重复创建；
3. DB 唯一约束阻止重复活动绑定；
4. 冲突后重查把并发失败转成成功结果；
5. 指出孤儿 placeholder 是剩余缺口。

### Q8：为什么第三方和设备绑定用 EXCLUDE，而手机号用 UNIQUE？

**简答**

第三方和设备需要“活动记录唯一、软删除后可重绑”，所以使用：

```sql
EXCLUDE (... WITH =)
WHERE (deleted = 0)
```

手机号当前用普通 `(phone_e164, app_name)` UNIQUE，软删除后仍占用唯一键，因此不能自然重绑。

**追问：是否必须用 EXCLUDE？**

不必须。PostgreSQL 也可以使用部分唯一索引：

```sql
CREATE UNIQUE INDEX ... ON ...
WHERE deleted = 0;
```

这是可选演进，不是当前实现。面试时应比较语义、运维支持和团队熟悉度。

### Q9：Redisson 故障时能否只靠数据库继续注册？

**简答**

当前不能。`tryLock` 异常没有降级分支，注册会失败关闭。若业务希望 Redis 故障时仍注册，需要明确允许绕过锁，并确保数据库事务与唯一冲突处理足够可靠；这属于演进策略。

### Q10：Snowflake 的风险是什么？

**简答**

单进程内实现能保证同毫秒序列唯一，并在序列溢出时等待下一毫秒；时钟回拨会直接抛错。真正的部署风险是多实例复用相同 workerId/datacenterId，可能生成重复 ID。

**演进方向**

实例编号集中分配、启动冲突检测、时钟监控，或改用独立 ID 服务/数据库序列。不能只说“用了 Snowflake 所以天然全局唯一”。

## 四、资料缓存和一致性

### Q11：为什么主资料和兴趣要拆缓存？

**简答**

主资料和兴趣变化频率不同，拆分后替换兴趣不必重写整份主资料，也能使用不同 TTL。当前主资料 24h，兴趣 7d。

**代价**

一次完整资料是两个来源的组合，不是同一时刻快照；写操作还会同时清三个 key，增加一致性边界。

### Q12：单人资料读取的 Cache Aside 是怎样的？

**简答**

先读主资料缓存，miss 查 `user_info` 并回填；再独立读兴趣缓存，miss 查 `user_interest` 并回填。主资料缓存不含兴趣，返回前才把兴趣挂到 VO。

**失败行为**

- 主资料缓存写失败只记日志，仍能返回；
- 主资料缓存读失败没有 catch，可能直接失败；
- 兴趣缓存读失败也可能阻断请求；
- 没有空值缓存和热点互斥重建。

### Q13：批量读取如何避免 N+1？

**简答**

对主资料缓存逐个 GET，收集 miss 后执行一次 `WHERE user_id IN (...)`；兴趣需要时再执行一次兴趣表 IN 查询。因此数据库主表和兴趣表没有按用户逐条查询。

**必须纠正的说法**

当前不是 MGET，也不是“一次 Redis 往返”；最多有 200 次 GET 和若干逐个 SET。兴趣批量读取不使用兴趣缓存。

**返回语义**

输入去重、按首次出现顺序返回、不存在用户静默跳过。调用方应按 userId 映射，不能按下标对齐。

### Q14：为什么“先写库再删缓存”仍可能不一致？

**简答**

方向本身符合 Cache Aside，但当前删除缓存发生在数据库事务提交之前：

```text
写 DB（未提交）
→ DEL cache
→ 其他请求可能用旧 DB 回填旧缓存
→ COMMIT
```

另一些写流程还会在事务内立即 `getProfile`，把未提交的新值提前写进 Redis。如果最后提交失败，缓存可能保留未提交值。

**演进方向**

在事务 `afterCommit` 失效缓存；需要更可靠时使用 outbox/变更事件。高一致场景可引入版本号或让缓存值携带版本，但这些都不是当前实现。

### Q15：Redis 删除失败会怎样？

**简答**

`evictAll` 没有吞异常。它在 Spring 数据库事务内被调用，Redis 异常会使方法抛出并触发 DB 回滚。但 Redis 已经执行成功的操作无法跟随 DB 回滚，因此这是跨资源、非原子边界。

### Q16：为什么不能把 `profile:big` 说成已使用？

**简答**

代码有 key 工厂和 get/set 方法，但业务路径没有调用，V1 也没有头像大字段列。这是“已预留”而不是“已支持”。

## 五、资料编辑和 onboarding

### Q17：资料编辑如何做动态更新和权限校验？

**简答**

caller userId 来自 gRPC Context；请求里若带其他 userId 会被拒绝。入口把空字符串和数值 0 转成 null，service 只把非 null 字段放进 patch，再通过 MyBatis-Plus wrapper 按物理主键 UPDATE。

**当前边界**

- 无法用空字符串清空简介等字段；
- 无法显式把 age/height 写成 0；
- 没有资料版本号，重叠字段最后提交覆盖；
- service 已重读资料，gRPC 层又重读一次，有冗余。

### Q18：onboarding 真的是一次性吗？

**简答**

产品意图和 Proto 注释说一次性，但代码没有检查 `pending==1`。任何已登录用户都可以重复调用并覆盖 gender、birthday，所以项目事实是“可重复 upsert”。

**事务边界**

主资料更新与非空兴趣替换在同一个有效事务内。内部兴趣方法虽是 self-call，但外层公共方法已经开启事务，因此 DB 原子性仍成立。

**特殊语义**

onboarding 的空兴趣列表表示保留旧兴趣；独立兴趣替换的空列表表示清空。面试中要能解释这种不一致是当前缺陷，而不是刻意设计。

### Q19：哪些字段校验是不完整的？

**简答**

普通资料编辑校验昵称、年龄、地区、简介、职业、教育和身高。onboarding 只完整检查昵称、性别、生日和简介，未统一校验地区/职业/教育长度、身高范围、生日是否未来日期或最低年龄。

**演进方向**

抽取共享 validator，入口与 service 保持同一口径，并用参数化测试覆盖边界值。

## 六、兴趣全量替换

### Q20：为什么兴趣适合 DELETE + INSERT？

**简答**

兴趣集合小、前端持有完整状态，还需要保存顺序。全量替换能直接表达最终集合，比新增/删除/调序三种增量命令简单。当前在一个事务内先删后逐行插入，失败整体回滚。

**数据约束**

`(user_id, tab_key, tag_key)` 唯一；`sort_order` 按请求顺序生成。

**代价**

- 每次都是物理删除和逐行插入；
- 并发请求 last-commit-wins；
- 没有版本冲突提示；
- gRPC 限制总数 50，service 却允许“图片 9 + 文字 50”，口径不完全一致。

### Q21：如何支持并发编辑检测？

**简答**

当前不检测。如果产品要提示冲突，可在用户兴趣集合或资料上增加 version，更新时使用 `WHERE version=?` 的乐观锁；失败后让客户端重新拉取并合并。这是演进方案。

## 七、封禁与故障策略

### Q22：封禁为什么有短缓存、运营集合和 DB 三层？

**简答**

DB `regulation_status` 是正式状态，运营 Redis Set 支持临时快速限制，5 分钟短缓存降低重复读取。查询顺序是短缓存、运营集合、DB。

**一致性边界**

缓存 NORMAL 也会命中并提前返回，所以刚加入运营集合的用户可能延迟到 TTL 过期才生效；仓库没有运营写入后清理短缓存的闭环。

### Q23：Redis 不可用时 CheckBan 会自动回源 DB 吗？

**简答**

不能笼统这么说。运营集合的 `SISMEMBER` 失败会按未命中继续，但短缓存 GET 和结果 SET 没有 catch，Redis 整体故障可能直接让检查失败。

**如何改**

先明确安全策略：

- 高风险业务可 fail-closed；
- 普通展示可在可观测告警下 fail-open；
- 正式 DB 状态是否必须始终可查；
- 运营集合故障时是否允许继续。

再分别捕获各层异常，而不是用一个模糊的“缓存降级”描述。

### Q24：当前 BanResult 有什么缺陷？

**简答**

service 使用 `BAN_REASON_USER_BANNED` 这类枚举名字符串，gRPC 转换器却匹配 `USER_BANNED`，所以可能出现 `banned=true` 但 reason=NONE。封禁时间也始终为 0；不存在用户被当作正常。

**演进方向**

内部直接传强类型枚举，避免字符串映射；补充不存在用户语义和封禁时间的数据来源。

## 八、头像和对象存储

### Q25：为什么采用两阶段直传？

**简答**

业务服务只负责授权、生成对象 key 和记录资料，客户端直接把二进制上传对象存储，避免 user-service 成为图片流量中转。confirm 用于验证对象并持久化引用。

**当前项目事实**

只完成扩展名、10MB 声明大小、用户存在性、对象 key 和目录前缀检查。presigned URL 带 `PLACEHOLDER`，没有真实对象存储调用；confirm 不 headObject、不落库，资料头像仍为空。

**不要说**

- “已接入 MinIO/S3”；
- “确认后会更新头像”；
- “缩略图 worker 已运行”。

这些都是设计或演进方向。

### Q26：confirm 只校验前缀够吗？

**简答**

不够。前缀只能阻止直接确认他人目录，还应验证对象确实由本次授权上传、存在、大小和媒体类型符合要求，并把 key 持久化。必要时保存一次性 upload session，防止旧 key 重放。

## 九、契约与跨服务可用性

### Q27：Proto 中有接口，为什么不等于服务支持？

**简答**

Proto 只生成基类和客户端 stub。服务端必须 override 方法并接到数据层。当前用户类型、DH 召回、附近 BH 召回都未覆写，默认返回 UNIMPLEMENTED。

**下游影响**

- match-service 把类型失败降级为 `-1`；
- 两类召回失败降级为空列表；
- im-service 把类型失败降级为 BH。

降级避免崩溃，但会把“服务未实现”混成“业务空结果”。

### Q28：如何改进这种契约先行问题？

**简答**

可选演进：

1. 未完成的实验接口不要进入稳定 Proto；
2. 调用方区分 UNIMPLEMENTED、UNAVAILABLE 和真实空集合；
3. 契约测试验证服务端确实 override；
4. 发布前跑跨服务集成测试；
5. 对关键降级建立指标，而不是只记 warn。

## 十、数据库和数据模型

### Q29：为什么同时有 `id` 和 `user_id`？

**简答**

`id` 是单表内部自增物理主键，便于本库更新；`user_id` 是对外稳定的 Snowflake 业务主键，跨服务和外键绑定都使用它。这样数据库内部实现与外部身份解耦。

### Q30：逻辑删除和外键如何交互？

**简答**

主资料的逻辑删除只是把 `deleted` 标记为 1，不会触发数据库 `ON DELETE CASCADE`；级联只在物理删除时生效。因此可能出现主资料查询不到、绑定仍为活动状态的组合，代码必须处理，而手机号/第三方命中分支当前缺少完整 null 防护。

### Q31：`updated_at` 是谁维护的？

**简答**

数据库为 `user_info` 和设备绑定建了 BEFORE UPDATE 触发器，MyBatis-Plus 还有 MetaObjectHandler。数据库触发器是最终兜底；应用自动填充则让普通 ORM 更新也带时间。要避免把两者说成严格同步时钟，它们都使用各自运行环境的“当前时间”，数据库连接配置为 UTC。

## 十一、代码质量与测试

### Q32：你会优先补哪些测试？

**优先级 1：正确性**

- 同一手机号/第三方/设备并发解析只产生一个活动绑定；
- 绑定失败时 placeholder 是否回滚；
- `touchLastOpenAt` 的 UPDATE 注解在真实 PostgreSQL 上能否执行；
- onboarding 主资料和兴趣任一步失败时整体回滚；
- 兴趣重复标签时旧数据是否恢复；
- 封禁 reason 映射。

**优先级 2：缓存一致性**

- 事务提交前并发读取是否回填旧缓存；
- Redis 删除/写入失败时 DB 与缓存最终状态；
- 批量缓存回填失败是否错误丢失结果；
- 主资料坏 JSON 和兴趣坏 JSON 的降级。

**优先级 3：契约**

- 17 个 Proto RPC 是否都有预期服务实现；
- missing user、重复 userId、200 边界；
- metadata 缺失和越权；
- 头像占位接口明确标记不可用。

### Q33：当前最值得先修的三个问题是什么？

**建议回答**

1. 注册创建与绑定改成真实原子事务，避免孤儿 placeholder；
2. 修复封禁 reason 和 Redis 故障策略，因为它关系访问控制；
3. 对未实现 RPC 做显式状态治理：补实现或从稳定调用链移除。

之后再处理事务提交后缓存失效、头像闭环和统一校验。

## 十二、规模化演进题

以下都属于演进选项，不是当前项目事实。

### 12.1 用户量增大后如何优化批量资料

- Redis pipeline/MGET 减少网络往返；
- 对 miss 继续单次 DB IN；
- 限制批量大小并设置调用 deadline；
- 用响应 Map 或显式 missingIds 消除下标歧义；
- 热点用户增加防击穿；
- 只有证据表明 PG/Redis 成为瓶颈时再考虑分片或搜索索引。

### 12.2 如何实现附近用户

- 先建立位置写入和更新时间语义；
- 小规模可用 PostgreSQL PostGIS/GiST；
- 高频在线位置可评估 Redis GEO；
- 复杂多维筛选可用独立检索索引；
- user-service 保持资料事实源，召回索引通过可靠事件同步；
- 必须定义位置隐私、精度和过期策略。

### 12.3 如何传播用户资料变更

- 数据库事务内写 outbox；
- worker 可靠投递用户资料变更事件；
- 下游按 userId + version 幂等消费；
- 失败可重试并可观测；
- 缓存失效也可由 afterCommit 或事件驱动。

当前没有 MQ/outbox，不能把这套方案说成现状。

## 十四、可复用答题模板

遇到任何系统设计追问，可以按以下顺序：

1. **业务特征**：数据规模、读写比例、唯一性、实时性、用户可见后果；
2. **当前事实**：具体类、方法、表、约束、Redis key 和事务边界；
3. **为什么这样做**：解决了哪一个核心冲突；
4. **失败边界**：DB、Redis、锁、网络、并发、重试时发生什么；
5. **当前缺口**：明确说出未实现、部分实现或风险；
6. **演进方向**：只有规模或需求成立时才引入更复杂方案；
7. **证据纪律**：不编造 QPS、延迟、事故结果和收益数字。
