# payment-service 面试问答（可靠性专版）

> 专项篇：聚焦"**每笔交易怎么保证可靠**"以及由此衍生的状态机、幂等、并发、Webhook、安全、订阅、可观测性、场景设计等高频问题。
> 通用版见同目录 `interview-qa.md`。

## 速查表

| 面试官问 | 一句话回答 |
|---------|-----------|
| 怎么保证不重复发？ | 状态机 `GRANTED` 锚点 + 订单幂等键 + DB 唯一索引 |
| 怎么保证不丢发？ | 状态机 `PAID` 兜底 + 定时补偿任务 |
| 怎么保证并发？ | 账户 version 乐观锁 + CHECK 约束 |

| 最大风险点？ | "Money path" 的状态推进和幂等 |

## 一、核心主线：每笔交易怎么保证可靠

### Q1：先做个整体介绍，payment-service 到底是干啥的？

**考察点**：是否把支付服务当成"叫 PayPal 接口"还是"账务核心"。

**标准答案**：
不是支付 SDK 包装，而是**价值账户中心**（订单 + 金币 + 订阅 + 钱包）。三层链路：第三方支付 → 内部订单 → 本地权益发放。match-service 只能通过 gRPC 调，不能碰库。

**追问：为什么不把所有逻辑放在 Gateway？**
Gateway 只负责接入和路由，不能持有支付、账务和权益规则。payment-service 是价值变更的唯一权威服务，其他服务只能通过 gRPC 调用，避免跨服务直接改账。

---

### Q2：用户支付成功后，怎么保证他一定能拿到金币？

**考察点**：支付链路的事务、幂等、补偿能力。

**标准答案**：
- 状态机拆 `INIT → PAID → GRANTED`，**收款 ≠ 发奖**
- 主动 verify + Webhook 两条路径，**共用同一套发奖逻辑**
- 发奖用订单幂等键 `order:<orderId>` + 数据库唯一索引
- `PAID` 但未 `GRANTED` 的订单由补偿任务重试

**追问：如果 capture 成功但本地发奖失败，钱已经收了呢？**
状态机设计就是为这种场景。订单停在 `PAID`，发奖失败由定时补偿任务扫描重试；同时客户端再点 verify 也会触发 `grantReward`，幂等保证不重复发。

---

### Q3：如果服务在"刚把订单推到 PAID 还没发金币"时挂了呢？

**考察点**：对"**至少一次重试 + 幂等 = 业务一次性**"的理解。

**标准答案**：
不能依赖进程内状态。**数据库状态是唯一权威**。重启后补偿任务扫 `PAID` 单继续 `grantReward`；发奖靠幂等键兜底，`GRANTED` 状态做去重锚点；外部动作（PayPal capture）不能放在会被回滚的事务里。

**追问：补偿任务跑挂了怎么办？**
补偿任务本身也要幂等：状态机条件更新 + 失败次数计数 + 超限人工对账。多个实例并发扫时靠乐观锁。

---

### Q4：客户端主动 confirm 和 PayPal Webhook 同时到，怎么避免双发？

**考察点**：幂等机制的实质。

**标准答案**：
数据库唯一索引 `(user_id, idempotency_key)` 是最终兜底。`grantReward` 进来先检查 `status == GRANTED`，命中直接跳过。但当前"先读后判"在并发下**有竞争窗口**，生产应补条件更新：

```sql
UPDATE payment_orders SET status='GRANTED'
WHERE order_id=? AND status IN ('INIT','PAID')
```

**追问：为什么不让前端只发一次？**
前端控制不可信：网络抖动、用户连击、APP 重启都会重复请求。幂等必须放在服务端。

---

### Q5：网络抖动导致客户端没收到 verify 响应，反复重试怎么办？

**考察点**：接口幂等 vs 链路幂等的区别。

**标准答案**：
- 客户端必须**带相同 orderId 重试**，服务端按订单号幂等
- `verifyPayment` 看到 `PAID/GRANTED` 直接返回，不重复 capture
- 幂等锚点在业务层（订单状态、流水幂等键），而不是看请求次数

---

### Q6：能不能只用 Redis 做幂等？

**考察点**：账务安全和缓存选型。

**标准答案**：
Redis 适合快速拦截，但**缓存丢失、过期、故障、主从切换**都会造成重复账务。支付/账务的最终正确性必须绑定到**权威存储**（PostgreSQL + 唯一索引）。实际项目里 Redis 适合放"瞬时态"（如 access token），不适合做账务唯一性。

---

### Q7：什么是"补偿"？你们怎么做的？

**考察点**：分布式事务的弱化方案。

**标准答案**：
不做跨服务 2PC，用**本地事务 + 状态机 + 定时补偿**。扫描 `PAID` 但未 `GRANTED` 的订单，重新调 `grantReward`；失败次数超阈值进人工对账。补偿任务本身也要幂等（防止并发扫单）。

---

## 二、支付订单状态机

### Q8：为什么是 `INIT / PAID / GRANTED / FAILED` 四个状态？为什么不直接 `SUCCESS`？

**考察点**：是否理解"钱已到 ≠ 权益已发"。

**标准答案**：
- `INIT`：订单已下，未收款
- `PAID`：PayPal capture 已确认收款
- `GRANTED`：金币/订阅本地发放成功
- `FAILED`：支付失败
- 拆分后可以扫 `PAID` 补偿发奖；`GRANTED` 是幂等去重锚点

**追问：只判 `GRANTED` 不够吗？**
不够。`PAID` 是已收款但权益未完成的中间态，不能当失败，也不能让客户端误以为已拿到权益。生产实现应建立订单权益表或条件状态更新，避免两个并发线程同时通过状态检查。

---

### Q9：`PAID → GRANTED` 是怎么保证只推进一次的？

**考察点**：状态机推进的原子性。

**标准答案**：
**当前实现**：`grantReward` 是"先读后判后写"，在并发下**有竞争窗口**。**生产实现**应使用条件更新：

```sql
UPDATE payment_orders SET status='GRANTED'
WHERE order_id=? AND status IN ('INIT','PAID')
```

更稳妥：增加 `grant_records(order_id, type)` 表，类型唯一索引。

---

### Q10：订单号怎么设计？第三方订单号和内部订单号为什么分开？

**考察点**：业务主键的认知。

**标准答案**：
内部 `orderId` 是**业务主键**（客户端/流水/重试都靠它）；`extTransactionId` 是 PayPal 订单号（对账、capture）。二者分离便于多通道，**绝不能把外部 ID 当内部业务身份**。

---

### Q11：状态能倒退吗？比如退款的 `PAID` 退回 `REFUNDED`？

**考察点**：状态机可逆性。

**标准答案**：
当前退款字段 `refund_status='NONE/PARTIAL/FULL'` 与订单状态正交。退款不应直接改 `status` 回退，只动 `refund_status` 和 `refunded_amount`。真正的退款还得补金币回滚、订阅回收，**当前实现缺口**（PRD F013 标占位）。

---

## 三、金币账户一致性

### Q12：为什么免费币和付费币要拆两个账户？

**考察点**：账户模型设计。

**标准答案**：
来源不同：免费币 = 签到/活动；付费币 = 充值。运营规则不同：免费币优先消耗、退款/过期策略不同。审计诉求不同：充值资金必须可追溯。物理拆分后，**消费算法 + 双账户扣减公式**才能真正稳定。

---

### Q13：扣币算法说一遍？

**考察点**：双账户扣减细节。

**标准答案**：

```text
freeTake = min(amount, freeBalance)
paidTake = amount - freeTake
newFree  = freeBalance - freeTake
newPaid  = paidBalance - paidTake
```

- 同一事务里写 EXPENSE 流水 + 更新账户
- 余额不足直接返回，**不写流水**

**追问：为什么先扣免费币？**
产品和成本策略：免费币通常有运营时效，优先消耗可减少用户长期囤积，也避免充值币被提前消耗后引发退款争议。

---

### Q14：两个请求同时扣同一个用户的 100 币，怎么不超扣？

**考察点**：并发控制。

**标准答案**：
- 账户行有 `version` 字段，@Version 注解
- 读后写走乐观锁，**影响行数 = 0 视为冲突**
- 最多重试 3 次，**重试耗尽抛错**
- DB 还有 `CHECK (balance >= 0)` 做最后一道防线

---

### Q15：乐观锁一定生效吗？

**考察点**：是否会看代码细节。

**标准答案**：
**不一定**。当前 `CoinAccountManager.updateBalance` 调 `updateById(entity)`，**但构造的新 entity 没有把读到的 `version` 设回去**。MyBatis-Plus 生成的 SQL 是不是带 `version=旧值` 条件需要确认；更稳妥写法：

```sql
UPDATE coin_accounts
SET balance=?, paid_balance=?, version=version+1
WHERE user_id=? AND version=?
```

拿到 `affected=0` 才算真正的冲突。"代码声明了 `@Version`" 不等于并发控制一定生效。

---

### Q16：用户第一次来，没账户怎么办？两个并发请求会不会都创建？

**考察点**：首单账户创建竞态。

**标准答案**：
`getOrCreate` 是"先查后插"，**有竞争窗口**。两个并发请求首次访问同一用户可能都走 `insert`。正确做法：主键冲突重查，或者 `INSERT ... ON CONFLICT DO NOTHING` 后 `SELECT`。

---

### Q17：流水为什么是 append-only？只更新余额不行吗？

**考察点**：审计账本的必要性。

**标准答案**：
余额是快照，流水是**审计账本**。不写流水无法回答"哪笔充值引起余额变化""是否重复发奖""对账差异"。append-only 支持对账、追责、补偿、构建用户视图。流水不应被 update/delete。

---

### Q18：幂等键怎么设计才合理？

**考察点**：幂等键的语义。

**标准答案**：
表达**一次业务动作**，不是请求随机 ID。好的例子：
- `order:<orderId>`：一笔订单的发奖
- `superhi:<userId>:<targetId>:<day>`：一次付费打招呼

同一动作重试必须复用同一个 key；不同动作不能用同一个 key。

---

### Q19：为什么幂等检查用先查再插而不是直接靠唯一索引冲突？

**考察点**：性能 vs 异常分支的权衡。

**标准答案**：
先查再插是**快速通道**，常见情况直接返回；唯一索引是**兜底**，并发窗口期的双写由它拦截。异常捕获 `DuplicateKeyException` 后重查已存在记录。同时省 Redis，又把正确性锁在账本。

---

### Q20：扣币的 SQL 真有把 version 条件写进 WHERE 吗？

**考察点**：是否真的会读 SQL 执行。

**标准答案**：
打开 MyBatis-Plus 的 `updateById` 生成的 SQL 看看。你的 entity 的 `version` 字段读出来后有没有塞到新对象里。如果没读出来，乐观锁就是**装样子的**。

---

## 四、第三方支付与 Webhook

### Q21：为什么把 PayPal 调用封装成 `PaypalExecutor`？

**考察点**：适配器 / 六边形架构。

**标准答案**：
OAuth token、REST URL、PayPal JSON、approval link 这些**协议细节**全部隔离在 Executor。业务层只表达"创建订单""capture"，不关心通道。未来接 Apple IAP / Google Billing / Stripe 只新增 Executor，不污染业务。

---

### Q22：PayPal 调用能不能放在 `@Transactional` 方法里？

**考察点**：事务边界 + 外部依赖。

**标准答案**：
**不应该**。HTTP 延迟会拉长事务占用连接；第三方超时 ≠ 业务失败，可能请求已发出，对方已扣款。正确顺序：先完成外部确认 → 本地状态机推进 → 本地事务发奖。当前代码 verify/capture 在事务里，是**生产化风险点**。

---

### Q23：Webhook 到底怎么保证安全？

**考察点**：回调安全审查（极可能被问）。

**标准答案**：
- 必须做：验签、event ID 去重、订单归属校验、金额币种校验
- 验签：PayPal 提供 `/v1/notifications/verify-webhook-signature` 接口，**当前代码 `verifyWebhookSignature` 已实现但 WebhookController 没调用**
- 回调进来的 `payload` 不能 Info 级别完整打日志（敏感信息）
- 缺一不可，否则任何人都能伪造回调发币

**追问：事件 ID 去重怎么实现？**
建立 `webhook_events(event_id PRIMARY KEY, event_type, received_at)` 表，插入成功才执行业务逻辑；重复事件直接返回 200 OK，不进入业务。

---

### Q24：为什么要既做主动 verify 又做 Webhook？

**考察点**：双通道设计意图。

**标准答案**：
- Verify = **即时体验**：用户支付完不用等异步回调就能看到结果
- Webhook = **最终一致 + 兜底**：用户关闭页面、客户端网络断都能收齐
- 两条路径必须**共用同一套发奖逻辑**，不能各做一套
- 摇合靠数据库状态 + 幂等键，不是 if-else

---

### Q25：Webhook 重复回调怎么办？

**考察点**：回调端的去重。

**标准答案**：
**当前实现没做** 事件 ID 去重。应当用 `event.id` 唯一索引记录接收过的事件；重复回调直接 200 OK 返回，不进入业务逻辑。PayPal 也可能在状态变更时重发同一事件。

---

### Q26：access token 缓存怎么处理？多实例会重复刷新吗？

**考察点**：缓存一致性。

**标准答案**：
当前 token 缓存在**进程内**，多实例各自刷新。通常可接受，但需要：

- 提前 60 秒刷新（避免临界过期）
- 连接超时、读超时、重试、熔断

长期生产方案：统一 Redis 缓存 access token（带集群锁）。

---

### Q27：手工拼 JSON 字符串有什么风险？

**考察点**：代码质量问题。

**标准答案**：
特殊字符（`"`、反斜杠、换行）会破坏请求体。`productName` 含特殊字符会让 PayPal 拒收。应当用 ObjectMapper 序列化对象，别用 `String.format`。当前 `escapeJson` 只是有限修补，不够。

---

## 五、订阅业务

### Q28：订阅续期从什么时候开始算？

**考察点**：时间语义。

**标准答案**：
- **未过期顺延**：`newExpire = oldExpire + durationDays`（不能从 now 算，否则吞剩余时间）
- **已过期**：从 now 重新开始
- 判 `expiresAt != null && expiresAt > now`

---

### Q29：档位只升不降怎么实现？

**考察点**：业务规则。

**标准答案**：
续期时 `newTier = max(oldTier, newTier)`，防止用户买低档把当前高档权益降级。这是产品策略，**应写在代码注释里**让人明确。

---

### Q30：同一用户并发续费两次会怎么样？

**考察点**：单行并发。

**标准答案**：
部分唯一索引 `WHERE deleted=false` 保证**只有一条 active 记录**，但**不保证**两个并发续费不会丢失更新（仍是 lost update）。需要：version / 行锁 / 原子 SQL 延长。

---

### Q31：怎么判断订阅有效？

**考察点**：判断逻辑。

**标准答案**：
`expiresAt != null && expiresAt > now && tier > FREE`，任一不满足 → 当 FREE 处理。用 `Instant` + `TIMESTAMPTZ` 全 UTC，**展示层再转本地**。

---

## 六、gRPC 与微服务边界

### Q32：什么能力应该走 gRPC？什么不该走？

**考察点**：服务边界。

**标准答案**：
- 走 gRPC：余额查询、扣币、加币、订阅查询/激活
- 不走 gRPC：商品列表、下单（这两个走客户端 HTTP）
- match-service 例如 SuperHi，**只提交幂等键和金额**，不写 SQL

---

### Q33：gRPC 接口幂等性怎么保证？

**考察点**：跨服务调用安全。

**标准答案**：
凡是带状态变更的 RPC 必须**由调用方生成稳定幂等键**。服务端按 `(userId, key)` 唯一索引判重。`ConsumeCoins` 必须有 key，否则客户端重试就重复扣币。

---

### Q34：gRPC `sendError` 真发出去了吗？

**考察点**：代码审查能力。

**标准答案**：
**当前实现是空函数**，只 catch 不 send。客户端既收不到业务错误码也收不到完成信号。应该用 `responseObserver.onError(StatusRuntimeException)` 或统一定义错误响应。

---

### Q35：`PurchaseCoins` 和 `getCoinLedger` 你怎么看？

**考察点**：是否识别占位代码。

**标准答案**：
这俩都是**遗留占位**，不能把"接口存在"误认为"功能完成"。上线前必须补齐：参数校验、错误码、超时、测试。客户调用前要么删，要么给明确 NOT_IMPLEMENTED。

---

### Q36：match-service 调你扣币失败，你要补偿吗？

**考察点**：跨服务一致性。

**标准答案**：
不做跨服务补偿。单据流水的幂等键就是 match-service 的"补偿开关"；失败后 match-service 查流水/订单，自己定业务补偿规则。支付服务只做权威账本变更。

---

## 七、事务与一致性

### Q37：你在代码里看到几个 `@Transactional`？覆盖了哪些场景？

**考察点**：事务边界理解。

**标准答案**：
- `verifyPayment` / `handlePayPalWebhook`：订单状态推进 + 发奖
- `addCoins` / `addPaidCoins` / `consumeCoins`：流水 + 账户
- 关键是**事务粒度**和**不要把外部 HTTP 包进去**

---

### Q38：跨服务分布式事务为什么不做？

**考察点**：事务模型选择。

**标准答案**：
2PC / TCC 引入复杂度和性能成本太高；业务上不需要强一致，可接受最终一致。用**幂等 + 状态机 + 补偿**替代分布式事务，对账任务兜底。

---

### Q39：订单校验、流水、余额、订阅，哪几个必须同事务？

**考察点**：事务内聚性。

**标准答案**：
- **必须同事务**：金币流水 + 账户余额更新（一起成功/失败）
- **可以独立**：订单状态推进（幂等键兜底）
- **完全独立**：订阅激活（独立幂等记录）
- Webhook 处理和 verifyPayment 走同一套代码最好保证一致性

---

### Q40：服务重启了，正在进行中的事务怎么办？

**考察点**：异常场景理解。

**标准答案**：
数据库事务本身有 commit/rollback 语义。已 `PAID` 未 `GRANTED` 的订单，重启后补偿任务继续。没法靠内存锁，靠**数据库唯一索引 + 状态机**。任何"内存 token"都不能用来做幂等。

---

## 八、安全与合规

### Q41：哪些字段是敏感的？日志里打印过吗？

**考察点**：日志安全。

**标准答案**：
PayPal `payload` 完整内容（可能含 PII、token、客户信息）。当前 `WebhookController` 把整个 payload Info 级别打出来，**风险点**。应只记录 eventId、eventType、orderId 摘要。PayPal client_secret、DB 密码不能进 git（红线）。

---

### Q42：怎么防止用户伪造别人的订单来查/取消？

**考察点**：权限校验。

**标准答案**：
- REST 接口应校验 `userId == 当前 token 中的 userId`
- gRPC 在 service 层判断 `order.userId == request.userId`
- 当前代码 `getOrder(String orderId)` 没校验用户归属，**安全缺口**

---

### Q43：退款链路在哪？退金币还是付费币？

**考察点**：业务完整性。

**标准答案**：
**当前实现没有完整退款逻辑**。退款设计：先建反向流水 → 扣回金币 → 触发订阅回收。要支持：仅退款不退订阅、退款关订阅、原路退回 PayPal。涉及金额计算、跨通道处理、人工审核。

---

### Q44：提现业务怎么设计？

**考察点**：钱包与提现。

**标准答案**：
**当前是占位**（PRD F013）。真实流程：绑定账户 → 申请 → 冻结余额 → 审核 → 打款 → 成功扣账 / 失败解冻。钱包流水 append-only，状态机 `INIT → AUDITING → PROCESSING → SUCCESS/FAILED/REJECTED`。幂等、防重复打款、风控。

---

## 九、性能与可观测性

### Q45：监控指标你打算看哪些？

**考察点**：运维意识。

**标准答案**：
- 订单：`create.success/failure`、`capture.latency`
- Webhook：`received/duplicate/invalid_signature`
- 发奖：`grant.success/failure`、`PAID.bucket_size`
- 金币：`consume.success/insufficient/retry_exhausted`
- 订阅：`activate.success`
- 提现：`pending/failed`

---

### Q46：补偿任务怎么实现？会不会把同一订单处理多次？

**考察点**：补偿并发。

**标准答案**：
定时任务每 N 分钟扫 `status='PAID' AND updated_at < now - 5min`。多个实例并发扫时：乐观锁 + 状态机条件更新。失败次数计数，超过阈值进人工队列。补偿任务本身也要记审计日志。

---

### Q47：Webhook 流量大不大？需要限流吗？

**考察点**：高可用。

**标准答案**：
PayPal 会重试到 200 OK 为止，**限流不能拒**。应做：快速 200 OK + 异步队列处理。重复请求直接去重。

---

### Q48：PayPal 挂了怎么办？

**考察点**：降级。

**标准答案**：
- 创建订单阶段：用户看到的"无法支付"提示
- Webhook 收不到：补偿任务轮询 PayPal REST API 查订单状态
- 业务：保留重试入口，配合人工对账

---

## 十、场景设计题

### Q49：设计一个可靠的充值发币系统

**回答框架**：
1. **需求澄清**：通道、币种、退款、订阅、到账延迟目标
2. **领域模型**：订单、商品快照、支付事件、权益发放记录、金币账户、金币流水
3. **状态机**：`INIT → PAID → GRANTED`,失败和退款独立建模
4. **支付确认**：主动 + Webhook + 验签 + 金额校验
5. **幂等**：事件 ID + 订单 ID + 权益类型组合唯一
6. **并发**：账户 version 或原子 SQL 扣减
7. **补偿**：扫描 PAID 重试,超限人工
8. **可观测性**：延迟、回调重复、发奖失败、余额变更
9. **安全**：凭据 Nacos、Webhook 验签、地址白名单、日志脱敏

---

### Q50：用户付款后 30 秒还没收到金币，怎么排查？

**标准答案**：
- 看订单状态：
  - `INIT`：PayPal 回调没到 / 没成功,等补偿
  - `PAID`：capture 成功但发奖失败或重启丢上下文
  - `GRANTED`：应该到了,查用户余额、看幂等键
- 看 webhook 日志：有没收到、签名校验、event type
- 看发奖日志：金币账户是否更新、乐观锁冲突
- 看下游：match-service 缓存？

---

### Q51：怎么防止用户刷金币（重复发奖）？

**标准答案**：
数据库唯一索引 `(userId, idempotency_key)` 是**强约束**。同一订单的幂等键 `order:<orderId>` 只能成功一次。不能信任前端传的金额/数量，永远以订单 `product.snapshot.coins` 为准。风控：同用户短时间多笔订单可以触发审核。

---

### Q52：如果要接 Apple IAP、Stripe，怎么改造？

**标准答案**：
新增 `AppleIapExecutor` / `StripeExecutor`，实现同一接口。`PaymentService` 用策略模式按 channel 选 Executor。Webhook 路由按 source 分发。商品表统一管理，订阅到期用同一套订阅服务。苹果的"续订通知"是另一个事件体系，需要单独处理。

---

### Q53：怎么从单库扩展到分库分表？

**标准答案**：
- 支付订单按 `userId` 哈希分片
- 金币流水按 `userId` + 时间分区（按月）
- 账户表按 `userId` 路由（同一个用户的所有金币操作在一库）
- gRPC 层无感知，靠 ShardingSphere
- 跨片操作（如全局对账）走离线任务

---

## 十一、代码审查与改进

### Q54：你看自己代码最不放心的地方是哪里？

**考察点**：是否诚实、能否识别缺口。

**标准答案**：
1. Webhook 验签未实际调用
2. `sendError` 没真正发送
3. 乐观锁 version 字段没传给 updateById
4. `getOrCreate` 首单并发
5. `getCoinLedger` / `PurchaseCoins` 占位
6. 完整 payload 日志敏感
7. 退款、提现、对账未实现

这种回答比只说"代码能跑"更可信，因为支付系统的核心评价标准是错误时能否止损、追踪和恢复。

---

### Q55：哪些操作必须做权限校验？

**标准答案**：
- `getOrder` / `cancelOrder` 必须校验 `userId`
- 运营加币、激活订阅要走 ADMIN 角色
- gRPC 调用应该用 mTLS / 内部证书
- PayPal Webhook 走 IP 白名单 + 验签

---

### Q56：上线前检查清单？

**标准答案**：
- [ ] Webhook 验签已生效
- [ ] 幂等键测试覆盖并发场景
- [ ] 乐观锁 SQL 真的带 version 条件
- [ ] 数据库迁移可重放（Flyway 状态）
- [ ] 监控告警配齐
- [ ] 错误码和 gRPC status mapping 一致
- [ ] 支付订单和金币流水对账脚本

---

### Q57：金额用 `BigDecimal` 还是 `double`？为什么？

**标准答案**：
必须 `BigDecimal`，金额是精确值。数据库用 `NUMERIC(16,4)`，对应 `BigDecimal`。PayPal 接口序列化也是 String，不用浮点。任何 `double` 计算都有精度损失。

---

### Q58：时区怎么处理的？

**标准答案**：
- DB 列：`TIMESTAMPTZ`
- JDBC init：`SET TIME ZONE 'UTC'`
- JVM：`-Duser.timezone=UTC`
- Java 代码：`Instant`，不用 `LocalDateTime`
- 对外返回：用 epoch milliseconds
- 展示层：客户端转本地时区
