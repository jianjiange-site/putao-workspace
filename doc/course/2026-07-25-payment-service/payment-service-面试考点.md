# payment-service 面试考点

> 回答原则：先讲业务与数据特征，再讲当前实现和取舍，主动说明失败边界，最后把改进项明确标成“演进方案”。不要把补偿任务、MQ、退款、提现或乐观锁说成已经实现。

## 1. 一分钟项目介绍

**问题：payment-service 在项目中负责什么？**

**精简回答**

payment-service 是约会业务的价值账户服务，不只是 PayPal API 的包装。它统一管理支付订单、免费/付费双金币账户和订阅权益，并通过 gRPC 给 match-service 提供订阅判断和幂等扣币。当前 PayPal 下单、主动确认、Webhook 验签、金币账务和订阅查询都有代码实现；提现、多支付通道、退款、对账、自动补偿和 gRPC 流水仍未完成。当前工作区还存在源码括号错误、重复 Flyway V1 和 PayPal 订阅来源约束不一致，因此我会把它描述为“核心模型已形成，但尚未达到可上线闭环”。

**为什么这样拆服务**

- 金币余额和订阅档位必须有唯一权威源。
- match/im 不应跨库改账，只提交业务动作和稳定幂等键。
- 外部支付协议封装在 payment-service 内，避免 PayPal JSON 和凭据扩散。

**常见追问**

- 为什么不放 Gateway？
- 为什么支付、金币和订阅放在一个服务？
- 哪些能力已实现，哪些只是表或协议预留？

## 2. 支付可靠性

### 2.1 为什么要区分 `PAID` 和 `GRANTED`

**核心回答**

业务上“第三方已收款”和“本地权益已到账”是两个事实。订单量不一定大，但事件会重复、乱序，外部成功也不能被本地事务回滚，所以需要：

```text
INIT → PAID → GRANTED
```

当前 `PAID` 表示 PayPal 已确认，`GRANTED` 表示订阅和金币均完成。拆开后才能识别“钱已收、权益未发”的中间状态。

**当前实现**

- 主动确认和 Webhook 都锁定 `payment_orders` 行。
- 状态更新带期望状态条件。
- 金币使用 `order:<orderId>` 幂等键。

**失败边界**

- 当前没有自动扫描 `PAID` 的任务，因此“可识别”不等于“能自动补偿”。
- 本地事务回滚不能回滚 PayPal capture。
- 订阅来源约束目前会阻断 PayPal 订阅商品发奖。

**演进**

增加支付事件表、权益发放表和任务/outbox，允许至少一次重试，并用唯一权益键保证业务一次性。

### 2.2 主动确认与 Webhook 同时到，怎么防双发

**核心回答**

这是一笔订单的两个并发入口，正确性应该落在权威数据库，而不是依赖前端或单机锁。当前代码对同一订单执行 `SELECT ... FOR UPDATE`，把两条链路串行；状态只能按期望值推进；金币流水还有用户加幂等键的唯一索引。

**要主动补充**

- 当前没有 webhook event id 去重，只能做到订单和金币层面的重复保护。
- 订阅没有独立的订单权益幂等记录。
- 行锁期间调用 PayPal，会放大锁持有时间。

**追问：为什么不用 Redis 锁？**

Redis 可做削峰或快速互斥，但锁和账务事务不在同一原子边界。数据库行锁与状态、流水都在权威库中，更容易保证和审计；高吞吐演进时再用事件表和异步执行缩短持锁时间。

### 2.3 Webhook 安全做了什么

**核心回答**

当前工作区不再是“只接收签名头但不验证”。Controller 把原始 payload、transmission 信息、证书 URL 和算法提交给 PayPal 的验签接口；缺 webhook id、凭据或签名头会拒绝。验签后还校验本地/外部订单号、金额和币种，capture 结果可选校验 merchant id。

**仍有缺口**

- 没有 event id 唯一表和重放审计。
- cert URL 由 PayPal 验签接口处理，本地没有额外白名单。
- Webhook 同步依赖 PayPal 验签和本地发奖，失败处理不够清晰。
- `CHECKOUT.ORDER.APPROVED` 分支吞掉异常后仍返回成功。

**演进**

验签后先持久化事件并快速返回，再异步处理；事件表记录 payload hash、处理状态、次数和失败原因。

### 2.4 capture 为什么不能长期放在数据库事务里

**核心回答**

外部 HTTP 延迟和数据库锁的时间尺度不同。当前主动确认先锁订单，再请求 PayPal；慢响应会占连接和行锁。更关键的是 PayPal 已成功、本地事务仍可能回滚，形成无法由 ACID 解决的跨系统不一致。

**当前取舍**

现实现换取了本地订单、订阅、金币的一次事务提交，但把外部网络包含在事务内，适合原型验证，不适合高可靠生产链路。

**演进**

外部确认得到不可变支付事实后，用短本地事务推进 `PAID`；权益发放由可靠任务重试，最终推进 `GRANTED`。

## 3. 金币账务

### 3.1 免费币和付费币为什么分开

**核心回答**

两类资产来源、退款和运营规则不同。免费币来自活动或赠送，付费币来自购买；分开后能实施“先免费后付费”、追踪充值资产，并为退款或过期规则保留空间。余额表保存快照，流水保存每次变更后的双余额。

**取舍**

双余额让更新和流水字段更复杂，但避免把真实付费资产与运营赠送混成不可审计的单余额。

### 3.2 当前怎么防并发超扣

**核心回答**

先说明事实：当前不是乐观锁。金币事务先用 `INSERT ... ON CONFLICT DO NOTHING` 初始化账户，再用 `SELECT ... FOR UPDATE` 锁住用户行；锁内重新检查幂等、判断总余额、拆分免费/付费扣减、写流水并更新账户。

```sql
UPDATE coin_accounts
SET balance=?, paid_balance=?, version=version+1
WHERE user_id=?;
```

SQL 没有 `WHERE version=?`，所以 `version` 只是递增计数，真正并发保护来自悲观行锁。

**追问：为什么还保留 `version` 字段？**

它现在只是账户修订计数，每次余额更新递增，可辅助审计或排查，但不参与 `WHERE` 条件。实体上的 `@Version`、无效重试和伪乐观锁更新方法已经删除，不能把这个字段解释为并发控制。

### 3.3 金币幂等怎么做

**核心回答**

调用方为一次业务动作提供稳定键。服务先查流水，取得用户行锁后再查一次，未命中才写账；数据库对 `(user_id, idempotency_key)` 建部分唯一索引。

**为什么两次查询**

- 第一次是快速返回。
- 第二次覆盖等待行锁期间其他事务刚完成的动作。
- 唯一索引是最终约束。

**必须指出的边界**

- 当前 `saveWithIdempotencyCheck` 不捕获唯一冲突，撞索引会回滚，不会自动反查返回。
- 唯一范围不含动作类型和请求摘要；相同键配不同金额或不同动作会被误判为重放。
- key 长度没有应用层校验。

**演进**

单独建幂等请求表或给流水增加业务域、请求 hash 和结果摘要；同键不同参数应返回冲突。

### 3.4 余额和流水为什么必须同事务

**核心回答**

余额是快照，流水是审计事实。只写余额无法解释来源，只写流水会让实时余额不一致。当前金币 Service 的流水插入和账户更新在同一事务，任一步失败都会回滚。

**失败语义**

- 余额不足：不写流水。
- 重复请求：返回第一次流水后的余额。
- DB 约束/更新失败：整个事务回滚。

### 3.5 行锁还是乐观锁怎么选

**回答框架**

先看数据热点和冲突率：

- 当前一用户一账户行，单次事务很短，行锁实现直观。
- 热点用户会串行排队，且当前支付链路中的嵌套调用会扩大事务。
- 低冲突高吞吐可用乐观锁，但必须在冲突后重新读取并重算双余额。
- 更高规模可用单用户顺序队列或原子条件更新，但流水和余额仍要保持同一提交边界。

不要声称项目做过吞吐对比；仓库没有基准测试或生产数据。

## 4. 订阅与缓存

### 4.1 订阅到期为什么不能只依赖固定 TTL

**核心回答**

订阅会随着时间自然失效，即使数据库没有写操作。当前缓存读取后仍检查 `expiresAt`，有效订阅 TTL 取 24 小时和剩余时长的较小值，FREE 负缓存 30 分钟。这样缓存不会跨过订阅到期时间长期返回高级权益。

**故障边界**

- Redis 异常回源数据库。
- payment-service 整体查询失败时，match-service 降级成 FREE。
- 这保护了权限边界，但会让已付费用户临时失去高级体验。

### 4.2 写缓存为什么在 afterCommit 删除

**核心回答**

如果数据库事务尚未提交就删除缓存，并发读可能查到旧 DB 值后重新写回缓存。当前付费档位更新注册事务同步，在提交完成后删除缓存，避免回滚时破坏原缓存。

**边界**

提交与删除之间仍有极短旧值窗口；当前不是完整的“写前删 + 提交后删”双删。

### 4.3 订阅并发续期有什么问题

**核心回答**

当前逻辑能正确处理单请求：未过期从原到期日顺延，档位只升不降；已过期从现在重新计算。但查询没有行锁或 version。两个并发续期读到同一个旧到期时间，可能各自计算后互相覆盖，丢失一次时长。

**为什么唯一索引不够**

部分唯一索引只保证每个用户一条未删除订阅，不能保证同一行的两次更新都被累加。

**演进**

使用 `FOR UPDATE`，或用数据库原子表达式从 `GREATEST(expires_at, now())` 顺延，同时返回实际 tier 和 expires_at。

### 4.4 为什么 PayPal 订阅现在会失败

**核心回答**

这是代码与迁移约束不一致：

- 代码和 proto 已定义 PAYPAL/STRIPE 来源。
- V6 CHECK 只允许 IAP_APPLE、IAP_GOOGLE、TEST、ADMIN。
- 支付发奖传入的还是大小写不同的 `"PayPal"`。

数据库约束会拒绝插入或更新，外层支付本地事务回滚。修复应通过新增迁移扩展 CHECK，并统一使用常量 `PAYPAL`，不能只改文档或绕过约束。

## 5. 微服务边界

### 5.1 match-service 如何使用 payment-service

**核心回答**

match-service 读订阅档位来计算 feed、滑动和 SuperHi 配额；SuperHi 需要金币时，把本地 `operationKey` 作为扣币幂等键。它先保存本地操作进度，再调用 payment-service，属于调用方编排的 Saga 风格流程。

**一致性边界**

- payment-service 只提交金币余额和流水。
- match-service 提交自己的操作、配额和匹配数据。
- 两边没有分布式事务。
- 重试依赖稳定 operation key，业务失败由 match-service 回滚或恢复自己的状态。

### 5.2 gRPC 失败语义有什么问题

**核心回答**

旧版 `sendError` 是空函数，当前工作区已经改成 `observer.onError`。但它把所有异常都映射为 `Status.INTERNAL`，传入业务 code 没使用，调用方难以区分参数问题、业务拒绝和依赖故障。

**其他边界**

- blocking stub 未设置逐请求 deadline。
- 通道使用 plaintext。
- 调用端附带内部 token，payment-service 服务端没有验证拦截器。

**演进**

建立错误映射表、deadline、服务身份认证和 TLS；仅对幂等读或带稳定键的写配置受控重试。

## 6. 数据库与发布

### 6.1 为什么重复 V1 是严重问题

**核心回答**

Flyway 以文件位置和命名识别迁移，不读取“本文件不参与启动”的注释。当前目录有两个 `V1__*.sql`，会造成版本冲突。支付库还配置了 `clean-disabled: false` 和 `clean-on-validation-error: true`，把迁移校验错误与潜在清库风险放在一起，是上线阻断项。

**正确处理**

- 合并学习版移出 Flyway 扫描目录。
- 生产禁用 clean。
- 历史迁移不改，新约束通过后续版本修复。
- CI 使用真实 PostgreSQL 从空库跑到最新版本。

### 6.2 配置安全有哪些事实

**核心回答**

PayPal 密钥字段本身允许由配置注入，但 `application.yml` 对 Nacos 地址、用户名和密码给了仓库内默认值。旧文档说“敏感值全部只用环境变量占位”不符合当前文件。服务端也没有验证下游附带的内部 token。

**演进**

密钥管理系统注入、仓库移除有效默认凭据、定期轮换，并在 CI 做 secret scanning。

## 7. 代码审查题：最应该指出的十个问题

按优先级回答：

1. `PaymentOrderManager` 当前括号错误，源码无法编译。
2. Flyway 同目录两个 V1，且账务库允许 validation error 时 clean。
3. PayPal 订阅来源与数据库 CHECK 不一致，订阅商品发奖回滚。
4. capture 在订单行锁和数据库事务内，外部成功无法随本地回滚。
5. 没有 Webhook event id 去重、权益记录和 `PAID` 自动补偿。
6. `CHECKOUT.ORDER.APPROVED` 吞异常后仍返回成功。
7. 金币已统一使用悲观行锁，但幂等唯一冲突仍没有反查恢复。
8. REST 用户身份、管理员能力和 gRPC 内部令牌缺少服务端鉴权。
9. gRPC 流水和遗留购买接口返回“成功样式”的空结果。
10. 订阅并发续期可能丢失更新，PayPal/Stripe source 协议与迁移不一致。

## 8. 场景设计题

### 8.1 设计可靠的支付发奖系统

建议按以下顺序回答：

1. **业务定义**：支付通道、商品快照、币种、退款、权益种类、到账时效。
2. **数据模型**：订单、支付事件、权益发放记录、账户、流水。
3. **状态机**：区分收款和发奖，不把所有成功压成一个状态。
4. **支付确认**：主动查询 + Webhook，验签、商户、订单、金额和币种校验。
5. **幂等**：event id 唯一、订单权益唯一、账务业务键唯一。
6. **事务边界**：外部 HTTP 不包在长数据库事务里；本地余额与流水同事务。
7. **恢复**：任务表/outbox 至少一次执行，失败重试和人工对账。
8. **安全**：服务鉴权、回跳白名单、密钥管理、日志脱敏。
9. **可观测性**：`PAID` 堆积、事件重复、发奖失败、账实差异。

明确说明：第 5 至 9 中有多项是本项目的演进目标，不是当前完整实现。

### 8.2 设计高并发金币扣减

先澄清：

- 是否只操作单用户账户；
- 免费/付费币扣减顺序；
- 是否允许负余额；
- 幂等键由谁生成；
- 是否要求同步返回。

然后给出两种路径：

- 中低冲突：`FOR UPDATE` + 流水/余额同事务，接近当前实现。
- 高吞吐：带版本或余额条件的原子更新，冲突后重算；热点用户可按 userId 串行。

不论哪种，都需要：

- 业务幂等记录；
- 同键参数一致性检查；
- 数据库非负约束；
- 对账和异常告警。

## 9. 高频追问速答

| 追问 | 回答要点 |
|---|---|
| 订单为什么不用 PayPal id 当主键 | 外部身份与内部业务身份分离，支持多通道和本地幂等 |
| 为什么余额不足不写流水 | 没有发生价值变更，失败请求不应污染账本 |
| 为什么流水 append-only | 审计、对账、幂等和追责需要不可变事实 |
| 为什么查询余额会写库 | 首次查询用 upsert 初始化零账户 |
| `version` 有什么用 | 当前只递增；没有版本条件，不能声称它实现乐观锁 |
| Redis 用在哪 | 只有订阅缓存；订单、金币、幂等 Redis key 均为未使用预留 |
| 有补偿任务吗 | 没有，仓库未发现定时任务、MQ 或任务表 |
| Webhook 验签了吗 | 当前工作区已远程验签；仍缺事件去重 |
| 提现完成了吗 | 只有余额读取，绑定/申请/历史直接未实现 |
| gRPC 流水可用吗 | 不可用，固定返回空页 |
| im 扣币正在使用吗 | 客户端类存在，当前源码未找到业务调用点 |
| 有生产性能数据吗 | 没有，不应虚构 QPS、延迟或优化收益 |

## 10. 复习优先级

### P0：必须能讲清

- `INIT → PAID → GRANTED` 的业务含义与当前缺少补偿的事实。
- 主动确认/Webhook 的订单行锁、状态条件更新和金币幂等。
- 金币实际是 `FOR UPDATE`，不是乐观锁。
- 双余额先免费后付费，以及流水与余额同事务。
- Webhook 当前已验签，但没有事件 ID 去重。

### P1：体现代码深度

- capture 已成功、本地回滚的边界。
- `FAILED` 更新因重新抛异常而回滚。
- `saveWithIdempotencyCheck` 名称与实际直接 insert 的差异。
- 订阅 afterCommit 缓存失效与并发续期丢失更新。
- PayPal source 与 V6 CHECK 冲突。

### P2：体现工程判断

- 重复 V1 和 Flyway clean 配置风险。
- gRPC 鉴权、deadline、错误映射。
- 商品硬编码与历史权益快照。
- 提现、退款、对账和补偿的演进顺序。

## 11. 可复用回答结构

遇到任意支付/账务问题，用以下结构组织：

1. **业务与数据**：钱、权益、事件、账户分别是什么，是否允许重复和延迟。
2. **当前事实**：真实类、方法、SQL、key、事务和调用方。
3. **正确性机制**：状态机、锁、幂等、唯一约束和审计流水。
4. **失败边界**：外部成功本地失败、回滚范围、重试和降级。
5. **当前限制**：明确已实现、部分实现、占位或阻断。
6. **规模化演进**：只把事件表、outbox、分片、MQ 等说成未来方案。
