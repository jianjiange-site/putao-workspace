# payment-service 业务清单

> 审阅基线：2026-07-30 当前工作区。结论以 `dating-server/payment-service`、`proto/payment/payment.proto`、数据库迁移和真实调用方代码为准；工作区内尚未提交的支付可靠性改动也计入本次审阅。

## 1. 服务定位

payment-service 是约会业务中的价值账户服务，负责把外部支付结果转换为平台内可使用的金币和订阅权益，并向内部业务提供统一的余额、扣币和订阅判断能力。

它当前覆盖四个领域：

- 商品与支付订单：展示固定商品、创建 PayPal 订单、确认收款、发放权益、查询订单。
- 金币账户：区分免费币与付费币，支持查询、增加、消费和流水审计。
- 订阅权益：维护 FREE、WEEKLY、MONTHLY、YEARLY 四档订阅及到期时间。
- 法币钱包与提现：数据结构和入口已预留，只有余额读取可用，其余流程仍是占位。

服务边界如下：

- payment-service 是金币余额和订阅记录的权威数据源。
- match-service 根据订阅档位计算卡片、右划和 SuperHi 配额，并在需要时调用 payment-service 扣币。
- im-service 已具备余额查询和消息扣币客户端，但在当前源码中未找到该客户端的实际业务调用点。
- PayPal 是当前唯一真正接通的外部支付通道。
- 服务内没有退款处理、自动对账、补偿任务、消息队列或提现打款流程。

## 2. 用户与系统角色

| 角色 | 主要诉求 | 当前边界 |
|---|---|---|
| App/Web 用户 | 看商品、创建订单、完成支付、查订单、查金币和订阅 | 接口直接接收用户编号，未看到统一鉴权或从登录态提取用户身份 |
| match-service | 查询订阅、按稳定业务键扣金币 | 查询失败按 FREE 降级；扣币失败由调用方业务处理 |
| im-service | 查询余额、按消息编号扣金币 | 客户端已实现；当前未发现业务调用 |
| PayPal | 创建/捕获订单并发送 Webhook | 当前代码会远程验签，并校验订单号、金额和币种 |
| 运营/管理员 | 发免费币、发付费币、激活订阅 | 能力已暴露，但当前服务没有角色校验或内部调用方鉴权 |
| 提现用户/审核人员 | 绑定收款账户、申请、审核、打款 | 除钱包余额读取外均未实现 |

## 4. 商品与购买

### 4.1 商品浏览

当前共有九个商品，均在服务启动时写入内存：

| 商品类别 | 商品 | 价格 | 购买结果 |
|---|---|---:|---|
| 金币包 | 100 / 550 / 1150 / 2400 / 6250 / 13000 Coins | USD 0.99 至 99.99 | 增加对应数量的付费币 |
| 周订阅 | Weekly Subscription | USD 9.99 | WEEKLY 7 天并增加 1000 付费币 |
| 月订阅 | Monthly Subscription | USD 29.99 | MONTHLY 30 天并增加 3000 付费币 |
| 年订阅 | Yearly Subscription | USD 79.99 | YEARLY 365 天并增加 8000 付费币 |

业务规则：

- 商品、价格、币种、金币数量和订阅时长均来自当前进程内定义，没有商品表或配置中心。
- 下单时会把商品编号、价格和币种写入订单，但发奖时会重新读取当前内存商品定义，并非读取完整的订单权益快照。
- 因此运行中修改商品定义后，历史已付款订单理论上可能按新定义发奖，这是当前模型的风险。

### 4.2 创建订单

用户选择商品后，服务先校验商品，再创建 PayPal 外部订单，最后保存本地 `INIT` 订单并返回支付跳转地址。

业务规则：

- 只有 PayPal 可用，其他通道会被拒绝。
- 内部订单号和 PayPal 订单号分别保存。
- PayPal 创建成功但本地订单保存失败时，会留下没有本地记录的外部订单。
- 同一次 PayPal 创建请求带内部订单号作为第三方幂等标识，但客户端重新发起下单会生成新的内部订单号，因此不是“用户购买动作级”的幂等。
- 回跳地址由调用方传入，当前未看到域名白名单。

### 4.3 支付确认与权益发放

收款确认有两条路径：

1. 用户支付后主动确认，服务锁定本地订单、调用 PayPal capture、核对订单号、金额、币种和可选商户号，再发放权益。
2. PayPal 发送异步通知，服务先远程验签，再定位并锁定本地订单，校验订单关联与金额币种，然后推进状态并发奖。

订单状态含义：

- `INIT`：本地订单已建立，尚未确认收款。
- `PAID`：第三方已确认收款，本地权益尚未全部完成。
- `GRANTED`：订阅和金币都已完成。
- `FAILED`：设计上表示支付失败；但当前主动确认失败时先写 `FAILED` 再抛异常，整个事务会回滚，因此该状态通常不会真正提交。

权益规则：

- 普通金币包只增加付费币。
- 订阅包先激活或续期订阅，再增加付费币。
- 金币发放使用 `order:<内部订单号>` 作为幂等键。
- 当前没有支付事件表、权益发放表、退款反向流水或 `PAID` 补偿任务。

当前阻断：

- 迁移脚本只允许订阅来源为 `IAP_APPLE/IAP_GOOGLE/TEST/ADMIN`，支付发奖传入的却是 `PayPal`。订阅商品发奖会触发数据库约束错误，并回滚本地订单、订阅和金币事务。
- 当前工作区的 `PaymentOrderManager` 方法括号不完整，源码本身无法通过 Java 编译。

### 4.4 查询订单

用户可以按内部订单号查询订单摘要。当前查询不要求用户身份，也不校验订单归属，因此知道订单号的人可以读取其他用户订单信息。主动确认路径已经校验请求用户与订单用户一致，但订单查询仍未补齐这条规则。

## 5. 金币账户

### 5.1 双余额模型

每个用户有一行金币账户：

- 免费币：活动、运营或赠送来源。
- 付费币：支付购买或明确的付费资产来源。
- 总余额：免费币与付费币之和。

消费顺序固定为“先免费、后付费”。这样可以保留两类资产的来源和余额轨迹，并让付费币审计更清晰。

### 5.2 查询余额

不存在账户时，服务会以数据库 `ON CONFLICT DO NOTHING` 的方式创建零余额账户，再返回免费币、付费币和总余额。

这意味着余额查询不是纯读操作：用户第一次查询会写入账户表。

### 5.3 增加金币

免费币和付费币分别增加，但遵循相同规则：

- 用户编号必须为正数。
- 数量必须大于 0。
- 幂等键必填。
- 同一用户的账户行会被数据库行锁锁住。
- 锁内再次检查幂等流水，未处理过才写流水并更新余额。
- 账户更新与流水写入处于同一数据库事务。

幂等键的唯一范围是“用户 + 键”，不区分免费发币、付费发币或消费类型。调用方必须自行使用明确命名空间；如果把同一个键误用于不同动作，当前服务会把已有流水直接当成该动作的历史结果。

### 5.4 消费金币

消费必须提供正数金额、有效用户编号和非空幂等键。

业务规则：

1. 总余额不足时不写消费流水，也不改变余额。
2. 总余额足够时，先扣尽可能多的免费币，剩余部分从付费币扣除。
3. 流水记录两类币的变动量和变动后余额。
4. 重复请求返回第一次处理后的总余额。

当前 match-service 的 SuperHi 使用其操作编号作为稳定幂等键；im-service 客户端使用 `im-msg:<messageId>`，但尚未发现业务调用点。

### 5.5 流水查询

用户可按页查询金币流水，按创建时间倒序返回，并同时计算总记录数。

当前规则缺口：

- 没有限制页码、页大小或最大页大小。
- 同一创建时间没有第二排序键，极端情况下跨页顺序可能不稳定。
- REST 查询可用，gRPC 查询仍返回总数为 0 的空页，不能视为同等实现。

## 6. 订阅权益

订阅档位从低到高为 FREE、WEEKLY、MONTHLY、YEARLY。

查询规则：

- 没有记录、档位不高于 FREE、到期时间为空或已经过去时，对外都视为 FREE 且未激活。
- 有效记录返回实际档位和毫秒级到期时间。
- FREE 结果缓存 30 分钟；有效订阅最多缓存 24 小时，且缓存有效期不会超过订阅到期时间。
- Redis 读写失败时记录告警并回源数据库，不阻断查询。
- match-service 查询失败时主动降级为 FREE，因此故障时用户会失去付费配额，而不会错误获得高级权益。

激活和续期规则：

- FREE 或更低档位被直接忽略。
- 第一次激活从当前时间增加购买天数。
- 未过期续费从原到期时间顺延，并保持较高的原档位，不因购买低档套餐而降级。
- 已过期续费从当前时间重新计算，并使用新购买档位。
- 数据提交后删除订阅缓存。

当前缺口：

- 没有校验用户编号、天数为正、来源是否合法或档位上限。
- 没有行锁、版本条件或原子顺延语句，并发续期可能丢失时长。
- 首次并发激活会由唯一索引拦截其中一个请求，但不会自动重查合并。
- gRPC 激活结果回显请求档位；若用户原来档位更高，回显值可能低于数据库实际档位。
- PayPal/Stripe 已出现在代码常量和协议中，却未加入数据库来源约束。

## 7. 钱包与提现

当前可读取法币钱包余额；没有钱包记录时返回 0。

以下能力只有接口、实体、表结构或常量，没有可执行的业务流程：

- 绑定 PayPal、Stripe 或银行账户。
- 校验提现余额与手续费。
- 冻结可用余额。
- 创建、审核、处理提现单。
- 成功扣账、失败解冻。
- 查询提现历史。
- 写入钱包流水。

因此不能把 `user_wallets`、`user_wallet_entries` 和 `withdraw_records` 的存在描述成“提现已实现”。

## 8. 权限、可见性和异常语义

当前 REST 和 gRPC 入口没有看到统一的身份认证或服务端内部令牌校验：

- REST 直接信任请求中的用户编号。
- 加免费币、加付费币、激活订阅等高风险能力没有管理员角色判断。
- match-service 和 im-service 会附带内部服务名和令牌元数据，但 payment-service 没有对应的服务端拦截器。
- gRPC 使用明文连接配置，调用端也没有设置逐请求 deadline。

REST 业务异常通常以 HTTP 200 包裹业务失败；参数异常和未知异常才分别使用 400/500。gRPC 异常统一映射为 `INTERNAL`，没有保留业务错误码。

## 9. 当前实现状态结论

| 领域 | 结论 |
|---|---|
| 商品 | 可用，但硬编码且缺少历史权益快照 |
| PayPal 下单 | 主流程存在，外部调用早于本地落单 |
| PayPal 验签与订单校验 | 当前工作区已实现，不再是“完全未验签” |
| 支付发奖 | 设计较完整，但订阅来源约束和当前编译错误会阻断实际运行 |
| 金币账务 | 使用数据库行锁、事务、幂等流水和余额约束；不是旧文档所说的乐观锁方案 |
| 订阅查询缓存 | 已实现，Redis 故障可回源 |
| 订阅续期 | 单请求规则已实现，并发与来源约束未闭环 |
| gRPC 金币流水 | 占位空页 |
| 遗留购买金币 | 占位空结果 |
| 提现 | 仅余额读取，其他能力占位 |
| 退款、对账、补偿、消息、定时任务 | 当前代码不存在 |
