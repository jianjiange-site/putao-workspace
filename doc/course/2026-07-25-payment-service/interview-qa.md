# payment-service 面试问答

## 一、项目讲解话术

### Q：介绍一下你负责的 payment-service

**标准答案：**

我负责的是约会应用的 payment-service，它不是简单的支付 SDK 包装，而是统一管理订单、金币和订阅权益的价值账户中心。用户选择商品后，服务先校验商品并创建内部订单，再通过 PayPal executor 创建外部订单；支付完成既支持客户端主动确认，也支持 PayPal Webhook。支付确认后订单先进入 `PAID`，再通过幂等的发奖流程增加付费币、激活订阅，全部成功后进入 `GRANTED`。另外，match-service 通过 gRPC 调用金币消费和订阅查询。金币账户拆成免费币和付费币，消费时先扣免费币，所有变更写 append-only 流水，并结合幂等键、数据库唯一索引和乐观锁处理重试与并发。

**追问：为什么不把所有逻辑放在 Gateway？**

Gateway 只负责接入和路由，不能持有支付、账务和权益规则。payment-service 是价值变更的唯一权威服务，其他服务只能通过 gRPC 调用，避免跨服务直接改账。

## 二、支付状态机与幂等

### Q：为什么要设计 `INIT`、`PAID`、`GRANTED` 三个状态？

**考察点：** 分布式状态机、支付一致性、补偿。

**标准答案：**

`INIT` 表示订单创建但没有确认收款；`PAID` 表示第三方已经确认收款；`GRANTED` 表示本地金币和订阅权益都已经发放。支付成功和发奖是两个不同阶段，第三方回调可能重复、网络可能超时、本地发奖也可能失败。拆开后可以扫描 `PAID` 订单做补偿，也可以用 `GRANTED` 作为“已经发过权益”的幂等锚点。重复确认遇到 `PAID/GRANTED` 会直接返回，不重复调用 capture。

**追问：只判断 `GRANTED` 不够吗？**

不够。`PAID` 是已收款但权益未完成的中间态，不能把它当失败，也不能让客户端误以为已经拿到权益。生产实现还应为发奖建立订单权益表或条件状态更新，避免两个并发线程同时通过状态检查。

### Q：主动确认和 Webhook 同时到达，如何避免重复发奖？

**标准答案：**

首先，订单状态和权益发放都必须由数据库作为权威；其次，金币发放使用 `order:<orderId>` 幂等键，数据库 `(user_id, idempotency_key)` 唯一索引保证并发重复请求最终只产生一条流水；订阅激活还应该增加独立权益幂等记录；最后，订单从 `PAID` 到 `GRANTED` 使用条件更新或锁，只有一个线程获得发放资格。失败的 `PAID` 订单由补偿任务重试。

**追问：为什么不只用 Redis 幂等？**

Redis 适合快速拦截，但缓存丢失、过期或故障时不能承担账务最终一致性。唯一索引在 PostgreSQL 中和流水同库，能把正确性绑定到权威账本。

### Q：订单号怎么设计？第三方订单号和内部订单号有什么区别？

内部 `orderId` 是本系统业务主键，用于客户端、流水幂等键和内部关联；`extTransactionId` 是 PayPal 订单号，用于调用第三方 capture 和对账。二者分开保存，避免把外部平台 ID 当作内部业务身份，也便于未来接入多个支付通道。

## 三、金币账户设计

### Q：为什么免费币和付费币要拆开？

**标准答案：**

因为二者来源和运营规则不同。免费币来自签到、活动等运营投放，付费币来自充值或购买；拆开后可以审计充值资产、实现免费币优先消耗、支持未来过期或退款策略。总余额是两个账户之和，但流水同时记录免费和付费两个维度的变动后余额。

### Q：扣币的具体算法是什么？

先校验 amount 为正，再检查幂等键。读取免费余额 `F` 和付费余额 `P`，若 `F+P < amount` 返回余额不足且不写流水；否则：

```text
freeTake = min(amount, F)
paidTake = amount - freeTake
newFree = F - freeTake
newPaid = P - paidTake
```

在同一事务中写 EXPENSE 流水并更新两个余额。

**追问：为什么先扣免费币？**

这是产品和成本策略：免费币通常有运营时效，优先消耗可以减少用户长期囤积，也避免充值币被提前消耗后引发退款或权益争议。实际项目应把这个顺序做成明确规则，而不是让调用方各自实现。

### Q：如何保证并发扣币不超扣？

账户行带 version，读取后更新使用乐观锁；受影响行数为 0 说明版本冲突，重新读取并重算，最多重试 3 次。余额不足在当前版本读取后返回。数据库还设置余额非负 CHECK，作为最后一道约束。

**追问：乐观锁一定生效吗？**

不一定。实体有 `@Version` 只是意图，必须确认 MyBatis-Plus 生成的 update 确实包含旧 version 条件，并正确递增 version。更稳妥的做法是显式执行 `UPDATE ... SET balance=?, paid_balance=?, version=version+1 WHERE user_id=? AND version=?`，检查影响行数；首次建账户还要用主键冲突重查或 `ON CONFLICT DO NOTHING`。

### Q：为什么流水要 append-only，不能只更新余额吗？

余额是当前快照，流水是审计账本。只更新余额无法回答“哪次充值导致余额变化”“一次消费是否重复”“支付订单发了多少币”。append-only 流水支持对账、追责和补偿，也可以根据流水校验余额。流水表不应被当作可随意修改的状态表。

## 四、第三方支付与 Webhook

### Q：为什么把 PayPal 调用封装成 `PaypalExecutor`？

这是适配器/执行器思路。业务服务只处理商品、订单状态和发奖，不关心 OAuth token、REST URL、PayPal JSON 和 approval link。这样未来接 Apple IAP、Google Billing、Stripe 时，可以新增通道执行器而不把第三方协议散落到 service/controller。

### Q：PayPal Webhook 有哪些安全问题？

当前代码接收了签名相关 Header，但尚未真正调用 PayPal 验签；这是不能直接上线的缺口。生产上要校验签名、证书来源、事件时间窗口、事件 ID 去重、内部订单号和外部订单号的绑定关系，并确认金额、币种和收款状态与本地订单一致。原始 payload 不能完整打 INFO 日志，应该脱敏或只记录摘要。

### Q：为什么既要主动 verify 又要 Webhook？

主动 verify 提供即时用户体验：用户支付后不用等待异步回调就能查询结果。Webhook 是第三方最终通知和异步补偿来源，覆盖用户关闭页面、客户端请求丢失等情况。两条路径必须汇聚到同一套状态推进和发奖幂等逻辑，不能各自实现一套发奖。

### Q：把第三方 HTTP 放在事务里有什么问题？

外部网络延迟会延长数据库事务并占用连接，第三方超时还可能让事务回滚，但外部动作是否已成功并不确定。更好的设计是先完成外部确认，再以本地状态机落库；发奖使用本地事务、权益幂等记录和补偿任务，不让长时间的第三方调用包住数据库事务。

## 五、订阅设计

### Q：订阅续费为什么从原到期时间顺延？

如果当前订阅还没到期，从 now 重新计算会吃掉用户已经购买的剩余时间。正确语义是 `newExpire = oldExpire + duration`；如果已经过期，才从 now 重新开始。档位取新旧最大值，避免买低档套餐把当前高档权益降级。

### Q：如何判断订阅有效？

查找用户未删除记录后，要求 `expiresAt != null`、`expiresAt > now` 且档位大于 FREE。任一条件不满足就返回 FREE/inactive。代码使用 `Instant`，数据库用 `TIMESTAMPTZ`，统一 UTC，避免跨时区误判。

**追问：部分唯一索引解决了什么？**

`user_subscription(user_id) WHERE deleted=false` 保证一个用户最多只有一条有效记录，避免并发或历史软删除数据造成多个当前订阅。但它不能解决同一行并发续期的丢失更新，仍需要 version 或行级锁。

## 六、gRPC 与微服务边界

### Q：哪些能力应该通过 gRPC 提供？

余额查询、扣币、加币、订阅查询和激活属于 payment-service 的领域能力，应该通过 `payment.proto` 对外提供。match-service 例如 SuperHi，只提交用户、金额和稳定幂等键；它不应该直接访问 payment 数据库或自己扣余额。

### Q：当前 gRPC 实现有哪些不足？

`GetCoinLedger` 仍是空分页占位，`PurchaseCoins` 是遗留空实现，不能把 proto 中声明的 RPC 视为已完成。另外 `sendError` 当前没有真正向 observer 发送响应或 gRPC status，异常处理需要统一，否则客户端可能无法正确识别失败。接口上线前应补齐参数校验、错误码、超时和测试。

## 七、场景设计题

### Q：设计一个可靠的充值发币系统

**回答框架：**

1. **需求澄清**：支持哪些通道、币种、商品、退款和订阅；用户是否允许重复购买；到账延迟目标。
2. **领域模型**：订单、商品快照、支付事件、权益发放记录、金币账户、金币流水。
3. **状态机**：`INIT → PAID → GRANTED`，失败和退款独立建模。
4. **支付确认**：主动查询 + Webhook，验签和订单金额校验。
5. **幂等**：事件 ID、订单 ID、权益类型组合唯一；金币流水使用业务幂等键和数据库唯一索引。
6. **并发**：账户版本号或数据库原子扣减；余额不足不落消费流水。
7. **补偿**：定时扫描 PAID 未 GRANTED，重试失败权益；超过次数进入人工对账。
8. **可观测性**：订单延迟、回调重复、发奖失败、余额变更和对账差异指标。
9. **安全**：凭据放配置中心，Webhook 验签，回跳地址白名单，日志脱敏，防越权查订单。

### Q：如果发奖过程中服务重启怎么办？

不能依赖内存状态。订单已是 `PAID` 时，重启后由补偿任务继续处理；金币发放通过订单幂等键，订阅发放通过独立权益记录，重复执行只返回已有结果；全部权益完成后再把订单置为 `GRANTED`。这样允许“至少一次重试”，通过幂等达到“业务上只生效一次”。

## 八、代码审查与改进题

### Q：你从当前实现中发现了哪些需要改进的地方？

我会主动区分已实现和占位部分：

1. PayPal Webhook 的验签参数尚未实际使用，必须补验签和事件去重。
2. `PaymentGrpcService.sendError` 没有完成真正的错误响应，需要统一 gRPC error mapping。
3. gRPC 金币流水分页和遗留购买接口仍是占位。
4. 商品配置硬编码在 `@PostConstruct`，生产应进入商品表或配置中心，并保存订单商品快照。
5. 发奖状态判断需要原子化，订阅和金币要分别具备幂等记录。
6. PayPal REST 请求应使用超时、重试/熔断和结构化序列化，避免手工拼 JSON。
7. `CoinAccountManager` 的乐观锁更新需要确认 version 条件确实进入 SQL；首次建账户需要处理并发插入。
8. 日志不能完整打印 PayPal payload，敏感配置不能进代码仓库或普通日志。
9. 提现、退款、对账、人工补偿还没有完整实现。

这种回答比只说“代码能跑”更可靠，因为支付系统的核心评价标准是错误时能否止损、追踪和恢复。

## 九、面试最后总结

> 我会把 payment-service 讲成一个“可靠账务变更系统”，而不是一个支付接口。它用订单状态机隔离第三方收款与本地发奖，用数据库唯一索引和业务幂等键抵抗重复请求，用乐观锁保护单用户余额并发，用双账户和 append-only 流水支持运营规则与审计，再通过 gRPC 把价值能力收敛到一个权威服务。当前实现已经覆盖主链路，但 Webhook 验签、原子发奖、提现、退款、对账和部分 RPC 仍需要生产化补强。
