# IM Service 业务清单

> 依据 `dating-server/im-service`、`proto/im/im.proto`、数据库迁移、mobile-gateway 与 match-service 当前代码整理。代码优先于旧设计稿。
>
> 状态口径：**已实现**、**部分实现**、**占位**、**契约已定义但缺失实现**、**配置存在但未使用**。

## 一、模块定位与边界

IM Service 的目标是把 OpenIM、实时通话令牌、消息业务规则和在线状态收口在一个服务中。当前代码已经搭出令牌、回调处理、在线状态和定时清扫的主体，但完整聊天闭环尚未形成。

当前边界：

- App 的聊天长连接由 OpenIM 承担，IM Service 不维护 WebSocket。
- mobile-gateway 暴露“获取 IM 登录凭证”和“获取通话凭证”两个用户入口。
- match-service 依赖 IM Service 获取在线/离线信号，并计划通过它完成建会话、系统消息和数字人开场白。
- IM Service 通过 gRPC 查询用户类型、余额并扣金币，通过 HTTP 调 OpenIM。
- PostgreSQL 保存消息镜像、在线会话历史和 ShedLock 锁；Redis 保存当前在线集合和用户类型缓存。

必须先理解的现状：

1. proto 声明了 9 项能力，服务端只覆盖其中 6 项；其中“发送消息”仍返回伪造结果。
2. OpenIM 回调内部处理代码存在，但仓库内没有找到 mobile-gateway 的回调入口；适配器也没有实现其接口，因此当前链路不可达。
3. 消息后处理会尝试落库，但没有填充数据库必填的 `route_type`，实际插入会失败。
4. AI 回复只是阻塞 2 秒后发送固定英文占位内容，没有调用 ai-chat，也没有 typing 续命和分段。
5. IM Service 当前源代码与 proto 在通话对端 ID 类型上不一致，按当前生成代码会出现编译错误。

## 二、用户与系统角色

| 角色 | 期望行为 | 当前状态 |
|---|---|---|
| 真人用户（BH） | 登录 OpenIM、发送聊天、发起一对一通话 | IM 登录凭证部分实现；聊天业务钩子不可达；gateway 通话入口为空实现 |
| 数字人（DH） | 由系统代发回复，不参与真人扣费和反导流 | 路由判断部分实现；发送前 DH 豁免未接用户类型服务 |
| mobile-gateway | 认证用户并代理令牌、回调 | 仅 IM token 入口调用下游；通话入口返回空对象；未找到回调代理 |
| match-service | 获取在线信号、建会话、发系统消息、触发 DH 开场白 | 在线/离线查询有服务端实现；另外三项下游缺失实现 |
| OpenIM | 提供账号、令牌、消息投递和回调 | HTTP 客户端存在；回调链路未闭合 |
| user-service | 提供 BH/DH 类型 | Redis Cache-Aside 客户端已实现，失败按 BH 降级 |
| payment-service | 提供余额查询和幂等扣费 | 客户端已实现；未真正配置代码中声明的 deadline |

## 四、用户侧能力

### F001 获取 IM 登录凭证

#### 功能描述

用户进入聊天模块时，经 gateway 向 IM Service 申请 OpenIM token。IM Service 再向 OpenIM 获取用户 token，并把 token 和有效期返回。

#### 业务规则

- gateway 使用认证上下文中的用户 ID，不接受客户端冒充其他用户。
- 当前 gateway 没有读取用户昵称和头像，实际向下游传空字符串。
- 头像 key 若非空，会被拼到硬编码的 MinIO 域名。
- OpenIM 调用失败时，IM Service 不返回业务错误，而是返回空 token 和有效期 0；gateway 异常时也返回空 VO。
- 代码意图是“用户不存在时注册后重试”，但默认 `RestTemplate` 会先对 HTTP 500 抛异常，因此 500 分支通常到达不了；代码也没有显式的一次重试计数。

#### 用户交互流程

1. 用户打开聊天页面。
2. gateway 根据登录态取得用户 ID。
3. gateway 请求 IM Service 获取 token。
4. IM Service 请求 OpenIM。
5. 成功时 App 得到 token；失败时当前实现仍可能得到一个空结果，需要客户端自行识别。

#### 数据流转

认证用户 → gateway → IM Service → OpenIM。该流程不写 PostgreSQL 或 Redis。

#### 当前边界

- gateway 默认下游端口为 `19091`，IM Service 默认 gRPC 端口为 `19082`，必须依赖外部配置覆盖才能连通。
- gateway 每次创建新的 gRPC channel，未关闭且未配置 deadline。
- 懒注册不能视为已闭环能力。

### F002 获取一对一通话凭证

#### 功能描述

用户点击语音或视频通话时，系统应签发一个短期 JWT，使双方加入同一个 LiveKit 房间。

#### 业务规则

- IM Service 端设置 30 分钟有效期。
- token 声明允许加入、发布和订阅，并额外给出房间管理、创建权限。
- LiveKit key 未配置或签名失败时返回空字符串。
- 当前房间名按“当前用户 ID + 对方 ID”拼接；两端分别申请时顺序相反，会得到不同房间名。

#### 用户交互流程

1. 用户点击通话。
2. gateway 应调用 IM Service 生成 token。
3. App 使用 token 加入 LiveKit。

当前第 2 步没有实现：gateway 直接返回一个空 `CallTokenVO`，其 IM 客户端也没有通话 token 方法。

#### 当前边界

- 服务端实现本身存在 proto 类型不一致：proto 的对端 ID 是整数，gRPC 实现按字符串接收，当前源码不能与当前生成代码直接编译。
- JWT claims 是否符合当前 LiveKit SDK 约定没有测试证据。
- 普通用户被赋予 `roomAdmin` 与 `roomCreate`，权限范围偏大。

### F003 发送消息

#### 功能描述

该能力应允许 gateway 或内部服务通过 IM Service 代发普通消息。

#### 业务规则与当前行为

- 当前仅记录日志。
- 不校验发送方、接收方、内容或消息类型。
- 不调用 OpenIM，不扣费，不落库。
- 直接返回 `msg_<当前毫秒>` 和当前秒级时间戳。

因此它是接口占位，不应描述为可用的消息发送能力。

## 五、消息规则与派生行为

### F004 发送前安检

#### 功能描述

设计目标是在 OpenIM 真正投递前完成发送方识别、数字人豁免、文本反导流和聊天金币处理。

#### 业务规则

- 发送方 ID 无法解析时放行。
- 设计上 DH 应直接放行；当前 `isDigitalHuman` 固定返回 `false`，所以所有可解析发送方都按 BH 处理。
- 仅 `msgType == 1` 的文本执行联系方式检测。
- 检测 Instagram、Facebook、WhatsApp、Telegram 和 10 位样式的美国电话号码。
- 扣费默认开启，单条默认 6 金币。
- 异步模式先查余额：余额不足拒绝；余额查询失败则放行；余额足够则先放行、进程内异步扣费。
- 同步模式直接扣费；支付失败拒绝。

#### 用户可见结果

- 命中联系方式或余额不足时，理论上消息被拒绝。
- 支付服务在异步预检阶段不可用时，消息被放行。
- 异步扣费失败后消息不会撤回。

#### 当前边界

整条回调入口与适配器装配尚未闭合，所以这些规则当前不能被视为实际生效。

### F005 发送后处理

#### 功能描述

设计目标是在消息已由 OpenIM 发出后保存业务镜像，并根据 BH/DH 方向决定是否触发数字人回复。

#### 业务规则

- 先尝试保存消息，再判断双方用户类型。
- 仅 BH→DH 触发 AI 回复。
- 用户类型查询失败时按 BH 处理。
- 落库失败被捕获并记录，仍继续执行路由。

#### 当前行为与偏差

- 写库实体没有设置 `route_type`，而迁移脚本将其定义为 `NOT NULL`，因此普通插入会失败。
- 没有应用层先查去重或 UPSERT；重复回调依赖唯一约束抛异常后被统一吞掉，无法区分“重复”与“真实写失败”。
- AI 回复不调用 ai-chat，阻塞当前回调线程 2 秒，然后发送固定的 `"Hello! This is an AI reply."`。
- typing、分段、图片理解等配置存在，但代码未读取或执行。

### S001 业务自定义通知

#### 功能描述

内部可通过 OpenIM 管理员身份发送 typing 等自定义消息。

#### 业务规则

- 优先使用配置的 admin token，否则每次临时向 OpenIM获取。
- 发送类型固定为 100，内容是 `data` 的 JSON。
- 失败仅记录日志，不向调用者返回成功/失败。

#### 当前边界

传入的 `notificationKey` 只用于日志，没有序列化到消息载荷；客户端无法依靠统一 key 区分 `typing`、`match_success` 等类别。匹配成功和欢迎常量目前没有调用方。

## 六、在线状态能力

### F006 记录上线与下线

#### 功能描述

上线时把用户加入 Redis ZSet，并首次开启一条 PostgreSQL 在线会话；下线时回填离线时间和时长，再从 ZSet 移除。

#### 业务规则

- ZSet member 是用户 ID，score 是首次上线毫秒时间戳。
- `ZADD NX` 使同一用户已在线时不更新 score。
- 只有系统判定“首次上线”时才插入历史会话。
- 下线只有在 Redis 仍能查到上线时间时才更新数据库。
- 当前代码没有过滤 DH，多端登录也没有按 platform 维护引用计数。

#### 当前边界

- Redis 与数据库不在同一事务；`@Transactional` 只覆盖 PostgreSQL。
- Redis 写成功、数据库失败会留下没有 PG 会话的在线 member；后续上线因 NX 被认为已在线。
- 下线时 Redis 数据丢失会导致 PG 会话不关闭。
- 重复上线事件若时间戳完全相同，当前“读取 score 再比较”的判定可能再次当成首次上线。

### F007 查询新上线用户

#### 功能描述

match-service 按时间窗口拉取新上线用户，生成在线场景的 DH 互动计划。

#### 业务规则

- 从 Redis ZSet 按 score 范围查询，默认 limit 为 5000。
- 非数字 member 被过滤。
- 返回顺序是 score 升序。
- 当前查询的上下界都包含；契约注释却声明上界不包含。
- 契约写了最大 50000，但服务端没有夹紧上限。

#### 消费方影响

match-service 无论调用成功、返回空还是被 limit 截断，都会把游标推进到本次 `now`。因此服务失败或窗口超过 5000 条时，剩余用户可能永久跳过；边界又是闭区间，成功场景下窗口端点可能重复。

### F008 查询最近下线用户

#### 功能描述

match-service 按离线时间窗口拉取用户，生成离线场景的 DH 互动计划。

#### 业务规则

- 查询 PostgreSQL `offline_at`。
- 使用 SQL `BETWEEN`，上下界均包含，与契约的开区间上界不一致。
- 先按 `user_id DESC` 排序和 limit，再在 Java 中 distinct，因此返回数量可能少于 limit，也不是按离线时间推进。
- 没有分页 token 或稳定的 `(offline_at, id)` 游标。

#### 消费方影响

消费方同样会在失败、空结果或截断时推进时间游标，存在漏处理风险。

## 七、配对后的聊天副作用

### F009 建立会话

配对后幂等创建双方会话。当前只有契约和 match-service 调用代码，IM Service 未覆盖该方法；实际调用会得到 gRPC `UNIMPLEMENTED`。

### F010 发送系统消息

向配对用户下发匹配成功等系统消息。当前只有契约和调用代码，IM Service 未实现。

### F011 触发数字人开场白

让 DH 在配对后主动生成第一条消息。当前只有契约和调用代码，IM Service 未实现。

match-service 已把这三类动作放入 Outbox 重试，但下游缺失实现意味着重试不能完成业务闭环。

## 八、后台支持流程

### J001 孤儿在线会话清扫

- 默认每 30 分钟执行一次，可通过开关关闭。
- ShedLock 名称为 `presenceSweep`，最长持锁 5 分钟，使用数据库时间。
- 查询 `offline_at IS NULL` 且 `online_at <= now - 26h` 的会话。
- 每条会话被封顶为 26 小时，然后移除对应 Redis member。

当前风险：

- 一次事务加载并逐条更新全部孤儿，没有批次上限。
- 同一用户存在旧孤儿会话、但 Redis 中是新的在线会话时，清扫旧记录也会无条件 ZREM 新在线状态。
- 事务回滚不能恢复已执行的 Redis 删除。

## 九、存储与配置边界

### PostgreSQL

| 表 | 作用 | 关键约束 |
|---|---|---|
| `chat_messages` | OpenIM 消息业务镜像 | `message_id UNIQUE`、`route_type NOT NULL`、逻辑删除 |
| `user_online_session` | 上下线历史 | `offline_at NULL` 表示未关闭；当前没有“每用户仅一条打开会话”的唯一约束 |
| `shedlock` | 定时任务租约 | 主键为任务名 |

### Redis

| Key | 结构 | TTL | 作用 |
|---|---|---|---|
| `putao:im:presence:online` | ZSet | 无 | 当前在线用户及首次上线时间 |
| `putao:im:user:type:{userId}` | String | 10 分钟 | BH/DH 类型缓存，`0/1` |

### 配置存在但当前未形成能力

- RocketMQ 依赖和生产者配置存在，但没有 producer 或 consumer。
- Redisson Bean 存在，但 IM Service 业务代码没有使用。
- ai-chat host/port 与 AI 回复节奏配置存在，但没有 ai-chat stub 和真实生成调用。
- Micrometer/Prometheus 依赖存在，但旧文档列出的业务 Counter/Gauge 没有代码注册。

## 十、全局业务边界

- 当前不能声称“所有消息都会经过反导流、扣费和落库”。
- 当前不能声称“消息可靠落库”或“逻辑 exactly-once”。
- 当前不能声称“OpenIM 用户懒注册只重试一次”。
- 当前不能声称“typing 每 3 秒续命”或“AI 分段回复”。
- 当前不能声称“在线状态是单一权威源”；它是 Redis 与 PG 的非原子双写。
- 生产演进应优先修复编译与链路可达性，再讨论吞吐优化和多 Provider 扩展。
